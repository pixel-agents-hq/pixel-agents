# Pixel Agents — Compressed Reference

Pixel art office where AI agents (Claude Code terminals today, any tool tomorrow) become animated characters. Ships as a **VS Code extension** and an **`npx pixel-agents` standalone CLI** from the same source tree.

`CONTEXT.md` is the canonical glossary — read it for what terms like Agent, Sub-agent, Teammate, Lead, Adopt, or Headless agent mean here, and use its vocabulary in code, comments, and docs.

## Architecture

Strict layering: `core/` depends on nothing; `server/` depends only on `core/`; `webview-ui/` depends only on `core/`; `adapters/vscode/` depends on `core/` and `server/`. The standalone CLI never imports `adapters/vscode/` and vice versa.

## Distribution

Two artifacts from one source tree:

- **VS Code extension** (`.vsix`) — `pablodelucca.pixel-agents` on VS Code Marketplace and Open VSX. Bundles VS Code adapter + webview SPA + assets + hook scripts.
- **npm package** (`pixel-agents`) — `npx pixel-agents [--port 3100]` runs the Fastify server and serves the SPA on the same port. Bundles CLI + webview SPA + assets + hook scripts + `core/asyncapi.yaml` (so third-party clients can regenerate from it).

`package.json:files` allowlist controls the npm tarball: `dist/cli.js{,.map}`, `dist/webview/`, `dist/assets/`, `dist/hooks/`, `core/asyncapi.yaml`, `icon.png`. `dist/extension.js` is intentionally excluded since the VS Code entry ships through the `.vsix`.

## Communication Flow

Hub-and-spoke. The server is the single aggregation point for all agent activity, regardless of source.

```
Hook scripts ─POST /api/hooks/:providerId─┐
                                          ├─→ HookProvider.normalizeHookEvent()
JSONL transcripts ─FileWatcher─→ TranscriptParser ┤
                                                   ↓
                                              AgentEvent (canonical)
                                                   ↓
                                              AgentRuntime (dispatch on .kind)
                                                   ↓
                                           AgentStateStore (mutate)
                                                   ↓
                                              StoreEvents → broadcast
                                                   ↓
                          PostMessageTransport ──┤├── WebSocketTransport
                                 (VS Code)      (standalone browser)
```

The VS Code adapter wires `PostMessageTransport` against `acquireVsCodeApi()`. The standalone CLI exposes the same protocol over WebSocket at `/ws` with the webview SPA served from the same Fastify instance. **The protocol shape is identical; only the wire differs.**

Adding a new CLI integration is one subdirectory under `server/src/providers/hook/<id>/`: provider, optional `TeamProvider`, installer, hook scripts. Zero changes to the runtime, the UI, or any existing provider.

## Transport Abstraction

```typescript
export interface MessageTransport {
  send(msg: ClientMessage): void;
  onMessage(handler: (msg: ServerMessage) => void): () => void;
  readonly ready: Promise<void>;
  readonly state: TransportState;
  onStateChange(handler: (state: TransportState) => void): () => void;
  dispose(): void;
}
export type TransportState = 'connecting' | 'connected' | 'reconnecting' | 'disconnected';
```

`PostMessageTransport` reports `connected` for its entire lifetime. `WebSocketTransport` reconnects with exponential backoff (250 ms, 500 ms, 1 s, 2 s, 4 s, capped) and queues sends while disconnected. **Broadcasts sent while a client is disconnected are lost, never replayed**, so every reconnect (`transport/onReconnect.ts`) re-sends `webviewReady` and the webview takes that snapshot as the whole truth (`resyncFromSnapshot` in `useExtensionMessages`): agents it doesn't list are closed, and tools, statuses and sub-agents are dropped for the replay to rebuild — a live sub-agent returns on its old spot with no spawn effect (`OfficeState.detachSubagentsForResync`). Without this, a `subagentClear` missed while a phone slept left its sub-agent in the office until a reload.

`createTransport()` in `webview-ui/src/transport/index.ts` is the **only branching point** in the UI codebase. Everything downstream uses the `MessageTransport` interface and never knows which transport is active.

## Provider Abstraction

`HookProvider` (`core/src/provider.ts`) is the integration boundary. Today only Claude Code is implemented; the Claude provider supports every transcript/hook format up to **Claude Code v2.1.310** (current as of 2026-10-26 — Task-era `agent_progress` records, explicit and implicit teams, background-by-default Agent spawns, sidecar-backed background agents, interim background-agent notices, mid-session worktree moves: `relocated` / `worktree-state` records, an interactive session's transcript moved into the new folder's project dir). Newer CLI releases may add formats that need provider updates. The interface:

- **Required**: `normalizeHookEvent(raw)` → `{ sessionId, event: AgentEvent, where?: { cwd, transcriptPath } } | null` (`where` on every event: how a session that moved is noticed); `installHooks` / `uninstallHooks` / `areHooksInstalled`; `formatToolStatus`; `permissionExemptTools`, `subagentToolNames`, `readingTools` sets.
- **Optional file fallback**: `getSessionDirs(workspace)`, `getAllSessionRoots()`, `sessionFilePattern`, `parseTranscriptLine(line)`, `sessionMoveFromRecord(record)` (a transcript record saying the session moved: Claude's `relocated` / `worktree-state`), `buildLaunchCommand(sessionId, cwd, opts)`. Used when hooks aren't installed.
- **Optional MCP config**: `mcpConfigFile({ name, url, token })` — how an MCP server is handed to a launched session: the contents of the file a launch's `mcpConfig` names, in the CLI's own format (Claude: the `--mcp-config` JSON). Without it, the CLI's agents are offered no Pixel Office MCP.
- **Optional terminal input modes**: `terminalInputModes` — the input modes (bracketed paste, application cursor keys) the CLI's terminal UI is assumed to be in when its screen cannot be read (VS Code types a Message blind, `turnGuard`); absent = plain modes (`PLAIN_INPUT_MODES`).
- **Optional worktrees**: `worktrees?: WorktreeConvention` — the CLI's worktrees folder (path segments), `sessionDirName(folder)` / `worktreeOfSessionDir(dirName, repoDirName)` (how it files a worktree's sessions), optional `lockHolder(lockReason)` (the process a lock of its own names) and `symlinkDirectories(repoPath)` (folders its settings link rather than copy). One member, so one provider supplies all of it; `server/src/worktreeLocation.ts` `worktreesCli` picks it. Without any, our Worktrees live in `.pixel-agents/worktrees` and the CLI has no worktrees of its own.
- **Optional tutorial facts**: `skills` (a `SkillPackaging`: how the CLI loads a skill for one session, how it names and invokes it; absent = the Guide reads its brief from the `tutorial` tool), `autoPermissionMode` (safe actions without a prompt, risky ones still asked; Claude: `auto`; absent = the CLI's default mode — the Guide never launches with prompts skipped) and `mostCapableModel` (Claude: `opus`; absent = the user's default model): what the tutorial's Guide is launched with.
- **Optional team extension**: `team?: TeamProvider` for Lead + Teammates support.

`AgentEvent.kind` values: `toolStart`, `toolEnd`, `turnEnd`, `subagentStart`, `subagentEnd`, `subagentTurnEnd`, `progress`, `permissionRequest`, `sessionStart`, `sessionEnd`. The runtime dispatches on `kind`, never on CLI-specific tool names.

### TeamProvider (Lead + Teammates)

Optional extension for CLIs that support team workflows (Claude Agent Teams today). Semantic queries (`discoverTeammates`, `getTeamMembers`, `getTeamMetadataForSession`, `extractTeammateNameFromEvent`, `isTeammateSpawnCall`) — providers choose their own storage strategy.

Four teammate modes:

| Mode                            | Trigger                                          | Detection                                                                                                                                                                                                                                                                                                                                                                               |
| ------------------------------- | ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Basic subagent (teams OFF)      | `Task(...)` or `Agent(run_in_background: false)` | `subagentStart` with team gate not matched, or JSONL `agent_progress`                                                                                                                                                                                                                                                                                                                   |
| Inline teammate (teams ON)      | `Agent(run_in_background: true)` in-process      | `onTeammateDetected` → `discoverTeammates(projectDir, leadSessionId)`                                                                                                                                                                                                                                                                                                                   |
| Session teammate (teams + tmux) | `Agent(run_in_background: true)` in tmux pane    | Own session, own hooks, routes through normal flow                                                                                                                                                                                                                                                                                                                                      |
| Implicit-team agent (Claude 5)  | `Agent(...)` — background by default, NO flag    | Lead-side: spawn tool_result `agent_id: <name>@<team>` → `extractTeammateSpawnFromToolResult` sets lead `teamName`; teammate = own top-level UUID session tagged `teamName`/`agentName` on every record, discovered by `discoverTeammates(projectDir, leadSessionId, teamName)` and fast-attached in `onExternalSessionDetected` (bypasses the Watch All gate when the lead is tracked) |

Newer harnesses (Claude 5) never tag the LEAD's records with team metadata and never write `agent_progress`/`queue-operation` records for these spawns — the spawn tool_result and the teammate's own session (own JSONL, own hooks) are the only signals. The implicit team writes `~/.claude/teams/session-<8hex>/config.json` (its `leadSessionId` matches no transcript on disk — don't link by it). Own-session teammates are registered with the SessionRouter (`setTeammateRegisterCallback`) so their hooks route directly to them.

**Team generations on resume (last-wins latch)**: every CLI run of a session mints a FRESH implicit team, so a resumed lead's transcript carries spawn tool_results from several `session-<8hex>` generations. A tag-less lead re-latches to the newest spawn's team (`setTeamSwitchCallback` removes the defunct team's teammates); tag-derived identity (`teamNameFromTags`, set by the record-tags branch) is authoritative and never overwritten by spawn results. `linkTeammates` never badges a named teammate as LEAD — if only teammates are tracked, linking waits until the real lead is detected (prevents a phantom LEAD character when a teammate session is adopted before/without its lead). Restore drops `isTeamLead` from persisted agents that carry an `agentName`.

**Background spawns without a CLI team (sidecar-backed)**: `Agent(...)` spawns that never register a team take the async path — result "Async agent launched successfully. agentId: \<hex>" (no team anywhere), transcript + sidecar under `<projectDir>/<leadSessionId>/subagents/` (sidecar carries `agentType`/`description`/`toolUseId`, plus `name` when the spawn was named), completion via `queue-operation`, matched by `<tool-use-id>` OR by `<task-id>` (the launch result's `agentId`, kept beside the tool id in the lead's `backgroundSpawns`, `server/src/backgroundSpawns.ts`): a post-crash notice lists only task ids (`status: stopped`), and an agent revived with SendMessage completes under the SendMessage call's tool id. An **interim notice** ends nothing: a background agent that stops to wait on background work of its own (a background Bash, a Monitor) gets a completion-shaped notice each time it pauses — same `status: completed`, the tool id on the first one and only the task id after — that only its summary ("… is waiting on its own background work") and note ("may be interim") tell apart from the final one; the provider reads every notice, interim or not (`TeamProvider.readSpawnNotices`; the shared code never sees the notice format), and both the live path (transcriptParser) and the restart check (`stillRunningSpawns`) leave the spawn live until a notice that isn't interim. A SendMessage result carrying `resumedAgentId` (a stopped agent revived, e.g. by a lead resumed after a crash) makes that call a live background spawn of its own: the provider's `extractBackgroundAgentFromToolResult` recognizes both kinds of result (launch and revival), and the runtime handles them as one, ignoring a result whose task id is already live. The scan ties the sidecar to the SendMessage spawn by the task id the provider reads off its transcript name (`agent-<taskId>.jsonl` → `discoverTeammates` entry `taskId`, `liveSpawnToolIdOf`), because the sidecar's `toolUseId` still names the original spawn the new process never saw. `scanForBackgroundAgentFiles` classifies them by the sidecar `name` (`classifySpawn`) — the domain model's sole Sub-agent vs Teammate distinction (see CONTEXT.md):

- **Named → Teammate**: its own seated character, `agentName` from the sidecar `name`; the spawner gets `isTeamLead` + an `agentTeamInfo` broadcast (derived team — NO `teamName`, so config polling stays away) and the transient Subtask is ghost-killed via `subagentClear`. The child has `leadAgentId` + `spawnToolUseId`; it's removed on the completion queue-operation or lead sessionEnd (`removeTeammate` must NOT unregister its session — it shares the lead's).
- **Unnamed → Sub-agent**: the Subtask sub-character stays; the spawn's transcript is watched in a **shadow `AgentStateStore`** (`server/src/subagentWatch.ts`, owned by `AgentRuntime`, ids from 1 000 000 up) whose broadcasts are translated onto the main store as `subagentToolStart/Done/Permission` keyed `(leadId, spawnToolUseId)` — live activity on the sub-character, no protocol change. `agentToolsClear` on the shadow agent synthesizes `subagentToolDone` for still-live tools so the sub idles between turns. Never persisted, never announced.

The gate for both: the sidecar must match a LIVE spawn of the lead, by `toolUseId` or task id (anti-spurious; no teamName involved). A spawn whose CALL carries a `name` (`teammateSpawnToolIds`, unless explicitly `run_in_background: false`) is never classified before its launch result lands: its sidecar can appear first, and deciding then watched it as a Sub-agent for good. `scanForTeammateFiles` skips sidecars of live spawns so it can't race the classification. The lead's `backgroundSpawns` (tool id + task id) are persisted through the shared `server/src/agentPersistence.ts` (children never are — they're derived state the 1 s scan re-materializes after a reload; restore skips stale entries with `leadAgentId` but no `teamName`). The turn-end background-tool re-sends (transcriptParser, hookEventHandler, timerManager's `clearAgentActivity`) must include `toolName` + `runInBackground` (or the webview can't recreate the Subtask after `agentToolsClear`) and must skip tools whose spawn became a teammate character (`hasPromotedBackgroundAgent`, or a ghost Subtask appears next to it).

Teammate dismissal is driven by team config polling (`getTeamMembers(teamName)` is authoritative; members with `isActive: false` are treated as departed), by the teammate's own `sessionEnd` (own-session teammates), and by `sessionEnd` on the lead.

**Subtle gate (the one that bit us recently)**: in `webview-ui/src/hooks/useExtensionMessages.ts`, `agentToolStart` with `runInBackground=true` only creates a Subtask sub-character when the **parent has no `teamName`**. With a team, `onTeammateDetected` creates the teammate instead (and the gate prevents a ghost sub-agent). Without a team, the teammate path never fires and the basic Subtask sub-character is the only visible representation. The gate's blind spot — a TEAMED lead's unnamed background spawn — is covered by `subagentToolStart` creating the sub-character lazily when it's missing (`addSubagent` is idempotent); the same lazy path recreates subs after a panel reload.

### AgentStateStore

EventEmitter-backed container in `server/src/agentStateStore.ts`. Typed mutations, typed events (`agentAdded`, `agentRemoved`, `agentUpdated`, `broadcast`, `agentStatus`). **An agent's turn status is a store fact**: `setAgentStatus(id, { active } | { active: false, awaitingInput })` is the ONE way it changes — it sets `AgentState.turnStatus` ('active' | 'done' | 'waiting for input'), broadcasts `agentStatus`, and emits the `agentStatus` event (every report, repeats included); the hook handler, the transcript parser and the timers all call it, and nothing re-parses broadcasts to learn it. The broadcast layer subscribes once at boot and translates `StoreEvents` into `ServerMessage` over the active transport. **No module under `server/` calls a transport method directly.**

### SessionRouter and DismissalTracker

Two extracted classes that replaced ad-hoc module state. `SessionRouter` owns `session_id → agent_id` mapping, pre-registration event buffering, and pending external sessions. `DismissalTracker` unifies four legacy globals (`dismissedJsonlFiles`, `clearDismissedFiles`, `seededMtimes`, `pendingClearFiles`) into one class with typed reasons.

### HTTP + WebSocket Server

Fastify v5 with `@fastify/cors`, `@fastify/websocket`, and (in standalone) `@fastify/static`:

| Method | Path                           | Purpose                                                                                                                                                  |
| ------ | ------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| POST   | `/api/hooks/:providerId`       | Bearer-authenticated hook event ingress                                                                                                                  |
| POST   | `/api/usage/:providerId`       | Bearer-authenticated usage report (status line bridge)                                                                                                   |
| POST   | `/api/terminal/:agentId/files` | A file sent to an agent's terminal or a PC shell's (standalone, `?token=` + allowed Host like the terminal socket): saved on the host, its path answered |
| GET    | `/api/health`                  | Liveness: `{ ok, version, port, pid }`                                                                                                                   |
| GET    | `/ws`                          | Bidirectional protocol channel                                                                                                                           |
| GET    | `/*` (standalone only)         | Webview SPA via `@fastify/static`                                                                                                                        |

`/ws` is gated in **two tiers**, because messages over this socket launch shells, grant durable machine-wide hook consent, and rewrite persisted state.

1. **Connection** (`isAllowedWebSocketOrigin`): embedded requires the Bearer token; standalone requires a same-origin handshake. A missing Origin still connects (non-browser clients send none). This tier is weak by design — a DNS-rebound page sends `Origin` and `Host` as the same attacker-chosen name and IS accepted (`httpServerWs.test.ts` pins that).
2. **Privileged messages** (`standaloneTokenValid`, `ClientMessageContext.privileged`): proved by an out-of-band secret — embedded via its Bearer token, standalone via the server token in the `/ws` `?token=` query, which the CLI prints in the local URL and the SPA forwards (`webview-ui/src/transport/index.ts`). **Never a network position**: peer address, `Host` and `Origin` all ride the channel a proxy speaks, so a LAN-bound forwarder piping bytes to 127.0.0.1 satisfies all three. The token is a replayable bearer capability, not evidence of locality — it reaches browser history (Fastify's request log redacts it, `wsAuth.redactTokenQuery`), so the printed URL is documented to the user as a secret. Standalone persists it in `~/.pixel-agents/standalone-token` (0600) so a bookmarked URL survives restarts; `--rotate-token` replaces it (revoking every device at once; refused while another standalone server is running, since it would keep honouring the old one). The terminal socket (`/terminal/:agentId`) carries it the same way and both sockets decide privilege with ONE predicate, `wsAuth.standaloneHandshakeVerdict`: the token AND an allowed `Host` — loopback, a specific `--host`, or a name passed with `--allowed-host` (anti-DNS-rebinding defence in depth). The allowlist is explicit rather than "loopback when loopback-bound" because a reverse proxy (Tailscale Serve) forwards to 127.0.0.1 under its public name; a loopback-only rule forced `--host 0.0.0.0`, exposing the port and the token in transit to the LAN. **An unprivileged client is read-only**: it may load and watch the office (`webviewReady`) and NOTHING else — every other message is refused by one gate at the top of `handleClientMessage` (`refuseReadOnly`), so a new message type is privileged by default. Where the UI updates optimistically (settings toggles, hooks toggle, asset directories, area mappings), the refused client is re-sent the real state. A tokened connection under an unlisted Host is read-only too and logs the `--allowed-host` hint. A second standalone launch reuses a running server only when its access matches (`ServerConfig.standalone`: terminal on/off, bind host, allowed hosts) — otherwise `--no-terminal` would silently attach to a server with a shell.

The **hooks preference is persisted only after the install/uninstall settled and the on-disk result agrees** — writing it first strands the user when an uninstall fails: entries still firing, but a persisted hooks-off makes the next startup skip the consent/install path entirely.

Server discovery written to `~/.pixel-agents/server.json` with `{ port, pid, authToken }`. Multi-window safe: a second server detects an existing `server.json` and reuses or replaces it based on PID liveness.

### ClientMessageHandler

Single dispatch point for `ClientMessage`. ### ServerAgentState (server/src/types.ts)

`migrateVsCodeState` (VS Code adapter only) walks each known legacy key once with **verify-before-clear** semantics: write to file, read back, only then clear the legacy key. While anything remains unmigrated, activation shows a non-blocking warning.

Layout and character-profile writes go through ONE `writeJsonAtomic` (tmp + rename) beside ONE generic watcher (`jsonFileWatcher.ts`: hybrid `fs.watch` + 2 s polling) used for both `layout.json` and `characters.json`; the write marks every live watcher of that path, after it succeeded (a failed write throws and marks nothing), so no watcher re-reads our own write and no caller has to remember to say so — except a `/ws` client's `saveLayout`, written with `reportToWatchers` so the VS Code panel's layout watcher still hears of it. An external `characters.json` change that validates updates the cached list and is broadcast as `characterProfilesLoaded` without a `saveId`; one that doesn't validate is ignored.

## Agent Status Tracking

JSONL transcripts at `~/.claude/projects/<project-hash>/<session-id>.jsonl`. Project hash = the workspace path with every character that isn't a letter, digit or `-` replaced by `-` (`core/src/normalizeProjectPath.ts`, Claude Code's own rule), so a Worktree at `<repo>/.claude/worktrees/x` hashes to `<repo hash>--claude-worktrees-x`.

**JSONL record types**: `assistant` (tool_use or thinking), `user` (tool_result or text prompt), `system` with `subtype: "turn_duration"` (reliable turn-end signal), `progress` with `data.type`: `agent_progress` (sub-agent tool_use/tool_result, non-exempt tools trigger permission timers), `bash_progress` (Bash output — restarts permission timer), `mcp_progress` (MCP tool — same timer restart). Also observed but not tracked: `file-history-snapshot`, `queue-operation`.

**File watching**: 500 ms polling with partial-line buffering for mid-write reads. Tool-done messages delayed 300 ms to prevent React batching from hiding brief active states.

### Dual-mode detection

| Mode                     | Source                                                 | Detection                                                                                                                                                                                                                                                                         |
| ------------------------ | ------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Hooks** (preferred)    | Claude Code Hooks API → HTTP POST → `HookEventHandler` | Instant, reliable. Installed events are `CLAUDE_HOOK_EVENTS`. `UserPromptSubmit`/`TaskCreated` are deliberately NOT installed — they normalize to null, so installing them only forwarded prompt text to be dropped; `normalizeHookEvent` still tolerates them for stale installs |
| **Heuristic** (fallback) | Polling JSONL files                                    | Per-agent 500 ms JSONL polling for /clear detection; 1 s main scanner for terminal adoption; 3 s external scanner; 30 s stale check. Content-based /clear detection (`/clear</command-name>` in first 8 KB)                                                                       |

The `hookDelivered` flag (per agent) and `hooksEnabled` (global) gate timer logic. JSONL polling always runs in both modes for tool content (status text, animations); only permission (7 s) and text-idle (5 s) timers are suppressed by `hookDelivered`.

### Sub-agent permission detection (heuristic)

When a sub-agent runs a non-exempt tool, `startPermissionTimer` fires on the parent agent. If `PERMISSION_TIMER_DELAY_MS` (7 s) elapses with no data, permission bubbles appear on both parent and sub-agent characters via `agentToolPermission` + `subagentToolPermission` broadcasts.

`activeSubagentToolNames: Map<parentToolId, Map<subToolId, toolName>>` tracks which sub-tools are active for the exempt check. Cleared when data resumes, Task completes, or `turn_duration` arrives.

**Timing budget for tests**: the test waits for the bubble AFTER waiting for the "Subtask:" overlay. But the Subtask overlay appears when the parent's **Task tool_use** is parsed (scenario time T), while the timer only starts when the **sub-tool tool_use** in the progress record is parsed (~1 s later). Plus 7 s timer + 300 ms IPC/render slop = a wait timeout less than ~10 s is unsafe.

### Context usage (server/src/contextUsage.ts)

Every agent's context gauge. Fed from `message.usage` on assistant records by `processTranscriptLine`, broadcast as `agentContextUsage` and rendered by `ToolOverlay`.

- **Snapshot, not a total.** Context = the newest turn's `input_tokens + cache_creation_input_tokens + cache_read_input_tokens` — no output tokens, exactly as Claude Code's own `context_window.used_percentage` counts it. Summing turns measures spend, not occupancy, and misses the cached tokens that ARE the context (`input_tokens` is single digits once caching kicks in). Falls on compaction and `/clear` for free.
- **All-zero usage means "no news"** — synthetic records (API errors, interrupts) report zeros and must not blank the gauge.
- **/clear is a real 0.** The fresh transcript (`reassignAgentToFile`, read whole) resets the agent to 0 tokens and says so (`clearContextUsage`), and a reported 0 is re-sent on every connect (`contextReported`); since the server never forwards a meaningless zero, the office trusts any 0 it hears and draws it as a FULL bar, over the character and on its card alike (`contextUsedShare`, `Character.contextReported`). A resumed session keeps its gauge.
- **Sidechain rule**: a lead's sidechain records are its sub-agents' turns and must not move its gauge; a teammate's own transcript is sidechain top to bottom and would otherwise never report. Positional latch (`sawMainChainUsage`): once a file produces a main-chain turn, later sidechain records belong to someone else.
- **The window comes from the provider**, not from the runtime: `HookProvider.contextWindowForModel(model)` (Claude: 1M for the current line, 200k for Haiku and the older models, `undefined` for ids it can't place). Transcripts state usage but never the limit, and guessing 200k for a 1M model reads five times too full. `widenContextWindow` is the backstop for unrecognized models and unknown-larger windows — it only ever widens, since a context that doesn't fit disproves the assumption while a shrinking one proves nothing.
- **`seedContextUsage` runs once per agent in `startFileWatching`** — the single seam every watched agent passes through. Agents adopted or restored mid-session start at end-of-file, so without a tail read they'd have no gauge until their next turn.
- **The CLI's own number wins.** With Usage Bars on, the status line bridge also reports each session's `context_window` (`used_percentage` + `context_window_size`); `applyReportedContext` sets the agent running that session to it and keeps the reported window (`reportedContextWindow`) for its later transcript estimates, so the gauge reads what the status line reads.
- Sub-agents get no gauge: no session of their own, and the shadow store never forwards `agentContextUsage`.
- **Drawn as a health bar** (`office/ContextBar.tsx`, the card's and the label's alike): the fill is the context LEFT (full when empty, draining as it fills), the colour still warns by the share used, in the user's status line steps (green < 33% used, yellow — the usage bars' — to 66%, red past it); `data-context-pct` stays the share used (e2e reads it).

## PC shells

A PC opens a plain terminal on the host for the user (glossary: **PC shell**; why the PC is a manifest and not code: `docs/adr/0005`). It is built on the furniture contract (Asset System → **Interactive furniture**), so nothing below names the PC: any furniture declaring the `terminal` panel does the same.

- **Hover and click** (office, outside the layout editor, which clears the hover as it opens): `OfficeState.pieces.at` is the editor's own `furnitureAt` (a surface item wins over its desk), kept only when core's `pieceView` gives the piece a label or a click; a character or pet under the pointer wins. The mouse hovers (`pieces.hoverAt`: faint outline, `FurnitureLabel` with the name and ONE line — the first whose condition holds — pointer cursor only where a click is offered and the office isn't read-only); touch is two-step (`pieces.tapAt`: the first tap hovers, a second on the same piece clicks and clears the hover, a tap elsewhere clears it). A click resolves through `pieceView`: `openPanel` (the piece's live shell) › `agentTerminal` (the agent working at it, opened as its card would) › `choosePlace` (its Area has several Directories: `PcDirectorySelector`, one button each) › `newPanel` (one Directory: there; none or no Area: the default folder). Offered only where the office runs terminals (standalone with its terminal, or VS Code) and isn't read-only (`pcShells/usePcShellPanels.ts`). A shell that opens shows only in the office that opened it (its `pcShellReady`): the drawer opens on, and a launch is answered by, new AGENT panes alone (`terminalPanes.ts`).
- **One registry** (`server/src/pcShells.ts` `PcShellRegistry`, both surfaces) over a small backend each (below), fed the surface's one `OfficePlaceFacts` (`server/src/officeFacts.ts`, the MCP's too) and handling the messages with ONE `handlePcShellMessage` (clientMessageHandler on standalone's `/ws`, the provider for VS Code's webview). `/ws` offices of both surfaces get the list in their snapshot and keep shell cards in a reorder (`pcShells`, a `PcShellView`); only standalone opens or closes one over `/ws` (`pcShellControl`), VS Code's embedded server never.
- **Messages** (all privileged; standalone refuses them where it runs no terminal): `openPcShell { uid, directory? }` → `pcShellReady { id }` to the sender (a live shell's own id when the piece has one) or `pcShellRejected { uid, reason }` (shown as `PcShellRejectedModal`); `closePcShell { id, confirmed? }` → closed, or `pcShellCloseQuestion { id, command? }` to the sender while a command runs; `pcShellsLoaded { shells: [{ id, uid, furnitureType, directoryName? }] }` — the whole list, to privileged offices only (`PRIVILEGED_BROADCAST_TYPES`: a view-only office sees the agents, never the operator's shells — no card, no lit screen, no shell label), on every change and in each connect's snapshot, so a reconnect drops a shell that ended meanwhile. A shell's card is reordered with the agents' (`saveCardOrder` accepts its id) and `focusAgent` with its id shows it.
- **Folder**: `pcShellPlace.ts` — the named Directory (refused unless it is one of the piece's Area's), else the single Directory mapped to its Area, else the surface's default: home (standalone), the first workspace folder then home (VS Code). The Directories it reads are the ones the office is shown (`directories.ts` `shownHostDirectories`, as `directoriesLoaded`): with Show host Directories off (the default) the host's own folder is neither offered by the selector nor picked by the server.
- **Standalone** (`server/src/terminal/pcShells.ts` `StandalonePcShells`, composed in cli.ts beside the agents' `ptyManager`): the user's login shell (`$SHELL -l`, else the passwd shell, else `/bin/sh`; `ComSpec` on Windows) on the agents' terminal sessions, in process or in the PTY host, with an agent terminal's env (`terminalEnv(inheritedEnv(…))`: no CLI session markers, `PWD` its folder). So the terminal socket `/terminal/:id` and the file upload route serve it under the agents' gate, and it shows in the drawer (desktop) or on the terminal page (phone) like an agent's terminal. It is NOT an agent: never in the store, so no provider, session, transcript, hooks, look, seat or gauge, and the agents' tools (list_agents, read_agent_terminal, send_message, close_agent) never list or reach it. Agents reach shells only through the Pixel Office MCP's own shell tools (the `shells` capability, standalone only: see "Pixel Office MCP"), which drive this registry as an office does — the user sees the card and the lit PC (`pcShellsLoaded`), and no office is sent `pcShellReady` — and read and write a shell through `StandalonePcShells`' own `screen` / `write` (live shells only), the one owner of how a shell's terminal is read and written. The ×: an idle shell ends at once; with a foreground command (`ps` tpgid ≠ the shell's pid; a probe that can't tell counts as running, and so does a PTY-host shell whose pid hasn't arrived yet) the sender is asked first (`PcShellCloseDialog`: Keep Running / Close Shell = `confirmed`). `exit` (any end of its process) ends it the same way: card gone, screen off, everywhere. **Windows** has no probe: there the × closes a shell at once, running command or not. The agents' terminal seam (`ptyAgentTerminals`) refuses shell ids by construction.
- **VS Code** (`adapters/vscode/vscodePcShells.ts` `VscodePcShells`, vscode-free, tested in `pcShellsVsCode.test.ts`): an ordinary integrated terminal in the resolved folder, tracked like an agent's (announced, a card, its PC lit) until it closes however it closes; a click on its PC or its card shows it; the card's × disposes it with no question (closing a VS Code terminal is the user's own act). Not saved: its terminal is created `isTransient`, so VS Code's persistent sessions never bring it back after a reload — it ends with the window.
- **The label's × and deleting a PC**: a piece with a live shell shows a × on its Furniture label where this office may close it (as an agent's label does; the label then takes the pointer and the canvas keeps the hover while the mouse is on it, `FURNITURE_LABEL_SELECTOR`) — the card's × by another door. Deleting a PC in the layout editor (the delete button or key, `handleDeleteSelected`) is closing its shell: `closePcShellsThen` closes the live shells of everything the delete removes, then removes it; a running command asks the usual question ("Close Shell and Delete"), and Keep Running keeps the PC. Any other way a piece leaves the layout (the erase tool, an import, an agent's edit) leaves its shell running as a card (Lifetime, below).
- **In the office**: "panel in use" is computed from the announced list (`OfficeState.pieces.setPcShells`), never stored in the layout: the PC shows its "on" state, its label reads "Shell in <Directory>", a click reopens it. New agents are seated away from a PC with a live shell while another seat is free (`seatChoices`); a seat asked for by name or assigned by hand ignores that, and the PC then still opens the shell.
- **Lifetime**: a shell outlives what it was opened from — its piece leaving the layout (a card only, no PC lit) or its Directory being removed (the card keeps its name). Standalone saves the live shells in `standalone-state.json` `pcShells` (with their folder); at start `restore` reattaches those whose terminals the PTY host (`--pty-host`) kept, under the same ids and before any office connects (one with no saved record — the state file lost — as a card of its own: `Home`, no piece), and drops the rest. Without the PTY host they end with the server.

## Usage bars

Top-left of the office (right of the zoom buttons; on the phone, right of the menu button): how much of the Claude Code plan is left — a weekly bar over a 5-hour bar of the same size, told apart like a game's health and stamina all the way down: weekly green → yellow (≤50%) → red (≤20%), 5-hour blue → purple → red, the share left printed inside each (left-aligned, in the pixel number font), no panel behind. A pixel heart sits left of them (`usage/PixelHeart.tsx`: outlined, shaded, colours in `USAGE_HEART_COLORS`; the beat flashes a one-pixel-bigger frame over it, whole pixels, never a scale). Hovering any of it (on a phone: a tap, undone by a tap elsewhere — hover is off there, since a tap's emulated mouseenter would cancel its own toggle) makes the heart beat at a pace proportional to the WEEKLY share left (`USAGE_HEART_MAX_BPM` at full, slower as it runs down, still when empty) and shows each bar's name and reset time just right of it (on a phone, below the bars) ("Weekly · resets in 3d 11h", "5-hour · …") (the age of the numbers is the hover title). Claude Code hands out `rate_limits` ONLY to its status line (subscribers, after a session's first reply), so the data comes from a **usage bridge** (`HookProvider.usageBridge`): Settings → Usage Bars, after a confirm showing the provider's disclosure (the click is the consent — never installed silently, not tied to hooks consent), WRAPS the user's `statusLine` in `~/.claude/settings.json` (`statusLine` is one command, not a list): `node ~/.pixel-agents/hooks/claude-statusline.js --wrap <base64url of their command>`. The script runs their command with the same stdin/env/cwd and passes output + exit code through, and POSTs only `rate_limits` and the session's context share (`session_id`, `used_percentage`, `context_window_size`) to every live server. No status line → a bare bridge that prints nothing (which hides Claude Code's footer hints — disclosed). Off / VS Code uninstall restores their command byte for byte; a status line replaced after us is left alone; non-command shapes and hand-edited wraps are refused, and so, on Windows, is a status line of the user's own (the wrap runs it through Node's shell, cmd.exe there, not Claude Code's Git Bash or PowerShell; only a bare bridge installs). A bare bridge counts as our own output in the backup predicate. With no session running the bars keep the last report (persisted), a window past `resetsAt` shows full, and "updated N ago" says how old the rest is. A project-scope `statusLine` overrides ours, so sessions there don't report. Usage is account data: `usageLimits`/`usageBridgeStatus` go to privileged sockets only.

## Pixel Office MCP

The office's MCP server (glossary: **Pixel Office MCP**, "Pixel Agents Office MCP" in full, never "Office MCP"), offered to the agents the office launches once the user consents. Server id `pixel-office` (tool names `mcp__pixel-office__…`). Why it is injected per launch with per-agent tokens rather than installed or handed the server token: `docs/adr/0003`.

**Shape**: a Streamable-HTTP route, `POST /mcp`, on the office's own Fastify server beside the hook and usage routes — standalone and VS Code's embedded server alike (GET/DELETE → 405). Stateless: every request is authenticated afresh and served by a fresh MCP server bound to its caller, so a revoked token is refused on its very next call and read-only is read per call. No stdio bridge, no `/ws` client, no second copy of office state: tools call the runtime, store, layout persistence, launcher and terminals directly. `server/src/mcp/` owns it all:

- `composeOfficeMcp.ts` = `composeOfficeMcp(surface)`, the ONE composition for both surfaces: a surface gives its `OfficeFacts` (store, provider, layout read/write, catalogue, asset counts, Directories, seats, Area mappings), its `terminals` + `deliveryGuard`, and `launch` / `close` / `pcShells` (its PC shell registry, read and written: `McpPcShells`) / `tutorial` (its TutorialSurface) where it can; it gets one `OfficeMcpFeature` (`registerRoutes`, `setEndpoint` (null: a reused server, not this office's), `offered()`, `handshake(send, afterHooksAsks?)` (nothing unless `offered()`), `handleMessage`, `layoutSaved`, `clientGone`, `dispose`, and `configFor` / `revoke` for launches), the ONE `officeMcp?` that server.ts, httpServer.ts, clientMessageHandler.ts and the VS Code provider carry.
- `officeMcp.ts` = `OfficeMcp`, the ONE owner of the route, the tool table (`toolsFor`: only the tools whose `uses` the office supplies) and the per-agent token registry; its consent/status messages.
- `tool.ts` = the tool contract (`defineTool`: zod `input`, `changes` = refused while read-only, `uses` = the capabilities `run` calls (`office` is typed to them), `run(args, { caller, office, target })` → ok/refuse; `target(agentId)` defaults to the caller; `ok(value, images?)`: PNGs sent as MCP image content after the JSON text, labelled only in the JSON). `tools/` = one file per tool + `tools/index.ts` (`OFFICE_TOOLS`, the order agents see them; a new tool = its file + one line there).
- `officeOperations.ts` = the seam tools call, by capability (`OfficeCapabilities`: `agents`, `layout`, `messaging`, `visits`, `characters`, `directories`, `launch`, `close`, `shells`, `tutorial`; a surface's `OfficeOperations` has `agents` … `directories` and `tutorial` always, `launch` / `close` / `shells` only where it can — VS Code has none of the three, so it doesn't list launch_agent / close_agent or the PC shell tools). One module per capability, each with narrow non-optional deps: `agentsView.ts` (list_agents; `statusOf` = the permission bubble, else the store's `turnStatus`), `layoutOps.ts`, `messaging.ts`, `visitsOps.ts`, `charactersView.ts` (the `characters` capability's read side — list_wardrobe / list_characters, previews drawn by `characterArt.ts` — plus the ONE character resolver `findCharacter` (id, exact name, else ignoring case, or palette index; a shared name refused with the matching ids; `paletteOf` adds the external char_N.png palettes for launches) and the colour naming `namedColors` / `describeColor`), `directoryOps.ts` (the `directories` capability: list_directories' view and edit_directories' batch — the Directory modal's own save rules, `directories.ts` `withUserDirectory`, run on a copy of the user's Directories and this office's Area mappings, written once), `lifecycle.ts` (launch + close, `closeAfterTurn`), `pcShellOps.ts` (the `shells` capability: the PC shell tools over the surface's `PcShellRegistry` — `pcs()` for the PCs, `open` / `close` with the office's refusals and close question, `running` for `busy`; typing is `typeInto` with `SHELL_KEYS` = the Message keys + `ctrl+c` / `ctrl+d`, no sender tag, no screen token).
- `officeFacts.ts` = `OfficeFacts` (the surface's one `OfficePlaceFacts`, `server/src/officeFacts.ts`, shared with the PC shells, plus what only the MCP needs) + `officeSnapshot(facts)`: one per call — the layout read and migrated once (`layoutFromJson`), the catalogue, the seats with their holders (`seatOf`: the saved seat, else the given one — written once), the walk grid on first use — so one request sees one layout.
- `seatPlace.ts` = seat → tile + Area; `layoutView.ts` = get_layout / list_catalog's views; `layoutEditOps.ts` = edit_layout's ops; `layoutEdits.ts` = commit / undo / lock; `characterEditOps.ts` = edit_characters' ops (core's setPart / setColor / randomize on a copy; Directory defaults held by character id during the batch); `characterEdits.ts` = their commit (the Characters view's Save path, `commitCharacterProfiles`, then the batch's Directory writes on top of the delete's renumbering; all or nothing — a failed Directory write puts the roster back through `putBack`, undo's own step), the `charactersEditing` lock, and undo (`CHARACTER_UNDO_DEPTH` edits, each with the roster and touched Directories' defaults before/after; the newest restored only while both still hold what it wrote, so a Characters-view Save, a Directory save or a characters.json change since refuses it — surfaces call `charactersChanged()` after those; recency is not restored); `canonicalJson.ts` = the key-order-free compare both undos use; `agentLabel.ts` = how an agent is named — Nickname, else its character's name, else its Directory — for the Message tag and "Undo <agent>'s edit"; `consentCopy.ts` = the disclosure.

**Access** (`AgentMcpAccess`):

- **Injected at launch, never installed.** With consent granted, every launch and resume through the office's one launch path (standalone launcher; VS Code's terminal launch) gets `--mcp-config <file>`: the provider builds the argument (`buildLaunchCommand` `mcpConfig`; added to the user's MCP servers, never replacing them — no `--strict-mcp-config`; the starting prompt goes last, after `--`, since `--mcp-config` takes several values). Nothing is written to `~/.claude`. Agents adopted from outside the office never get it. Only Claude's launch command knows the flag.
- **Per-agent token.** `configFor(agentId)` mints a random token (`OFFICE_MCP_TOKEN_BYTES`) bound to that agent and writes the provider's `mcpConfigFile` for it (Claude: `{ mcpServers: { 'pixel-office': { type: 'http', url, headers: { Authorization: Bearer … } } } }`) to a fresh 0600 file under `~/.pixel-agents/mcp/<pid>-<rand>/agent-<id>.json` (never on the command line, where `ps` shows it; dirs of dead servers pruned at start). The registry is memory only: a token dies with its agent (`agentRemoved`), with the server (`dispose`), and all at once on a decline (`revokeAll`); `revoke` for a launch that never happened. The token IS the caller's identity — there is no other header. The master server token never reaches an agent. A request carrying `Origin` (a browser) is refused 403; an unknown token 401. A provider without `mcpConfigFile` writes no file, so its agents are offered no MCP: `configFor` mints nothing.
- **Consent** follows `docs/adr/0001`: config.json `officeMcpConsent` granted | declined (absent = unanswered = not injected), one config write per answer, Back revises. Asked on the Intro's choices step (`IntroChoices.tsx`) as one box beside the hooks and usage bars ones, all off to start, ticked = `allow`, left off = `decline`, its line and terms served by the server (`officeMcpConsentRequest` `summary` + `disclosure` — privileged sockets only, during the `webviewReady` handshake; `officeMcpConsentResponse` `allow` | `notNow` (back to unanswered, every token revoked; on the wire, not offered by the Intro) | `decline`); an office that finished the Intro before the ask existed shows the step with that box alone. Settings: an on/off switch (`setOfficeMcpEnabled`, the same disclosure as a confirm; off applies at once, no confirm) and a read-only switch (`setOfficeMcpReadOnly`, config `officeMcpReadOnly`); `officeMcpStatus` (privileged only) carries consent + read-only and is present only on a server that offers the MCP, so Settings shows the switches only there. Both effective at once for running agents. A read-only office (no token) reaches none of it.
- **Read-only** narrows the table at call time: tools with `changes` reply "read-only in Pixel Agents settings" (`OFFICE_MCP_READ_ONLY_REASON`).
- Claude Code's own MCP permission prompts still apply in the agent's terminal.

## Office UI

**Rendering**: Game state in imperative `OfficeState` class (not React state). Pixel-perfect: zoom = integer device-pixels-per-sprite-pixel (1x–10x). No `ctx.scale(dpr)`. Default zoom = `Math.round(2 * devicePixelRatio)`. Z-sort all entities by Y. Pan via middle-mouse drag (`panRef`). **Camera follow**: `cameraFollowId` (separate from `selectedAgentId`) smoothly centers camera on the followed agent; set on agent click, cleared on deselection or manual pan.

**UI styling**: Pixel art aesthetic — sharp corners (`borderRadius: 0`), solid backgrounds (`#1e1e2e`), `2px solid` borders, hard offset shadows (`2px 2px 0px #0a0a14`, no blur). CSS variables in `index.css` `:root` (`--pixel-bg`, `--pixel-border`, `--pixel-accent`, ...). Pixel font: FS Pixel Sans (`webview-ui/src/fonts/`), loaded via `@font-face`, applied globally.

**Pixel icons are 8×8.** Every UI icon is an 8×8 grid in `components/ui/pixelIcons.ts` (`#` = lit pixel, drawn in the text colour), rendered at `PIXEL_ICON_SCALE` whole screen pixels per icon pixel (2 → 16 px). Never scale an icon fractionally: blurred edges break the pixel look. `PixelIcon` also guards against the display doing it: at a browser zoom or scaled display (1.25x, 1.5x) it draws each icon pixel as the whole number of DEVICE pixels at or below `scale` (`components/ui/pixelSnap.ts`, ratio from `hooks/useDevicePixelRatio.ts`), else some rows come out a device pixel thicker than others. Position needs no help — the browser paints each box from a whole device pixel, so nudging one by its fractional offset shifts it a full pixel. To shrink one, step the whole-number scale down (`<PixelIcon name="close" scale={1} />`, 8 px — the roster cards' ×) or draw the shape smaller inside the 8×8 (`zoomIn`/`zoomOut`). Buttons take `icon="<name>"` and draw it left of the label, vertically centred.

**Numbers use the pixel number font.** A 3×5 font drawn as pixel art (`components/ui/pixelFont.ts` glyphs + `splitLabel`, `PixelText.tsx`): only number words ("73%", "-40", "3d 11h", "3x", "v1.5", "1 / 21", an upper-cased hex "#1E1E2E", a month "OCT 13", a moment ago "NOW" — `timeAgo` writes dates with `MONTHS`, never the locale's) become glyphs, everything else stays in FS Pixel Sans. Use `<PixelText text=… />` (`smaller` = one device pixel less per glyph pixel, a crisp in-between on 2x/3x screens — the sidebar's times) wherever the UI prints a number (history times, slider values, zoom level, version, usage bars); a text field shows it through `PixelInputText` (the field's own text is transparent until focused). A new character needs its glyph and the `NUMBER_WORD` pattern.

Custom ESLint rules (`eslint-rules/pixel-agents-rules.mjs`) enforce: `no-inline-colors` (hex/rgb/rgba/hsl/hsla literals only in `constants.ts`), `pixel-shadow` (must use `var(--pixel-shadow)` or `2px 2px 0px`), `pixel-font` (must reference FS Pixel Sans). All `error`-level — they block PRs.

**Characters**: FSM states — active (pathfind to seat, typing/reading animation by tool type), idle (wander randomly with BFS, return to seat after `wanderLimit` moves). 4-directional sprites, left = flipped right. Tool animations: typing (Write/Edit/Bash/Task) vs reading (Read/Grep/Glob/WebFetch). Sitting offset: characters shift down 6 px in TYPE state. A TYPE character that isn't active (resting in its chair after wandering, or held by `seatTimer` — a usual rest is `restInChair`) shows the **seated** frame instead of typing; helpers (sub-agents) never do — they keep typing through the gaps between tools and stand once idle. Z-sort uses `ch.y + TILE_SIZE/2 + 0.5` so characters render in front of same-row furniture but behind lower-row furniture. **Chair z-sorting**: non-back chairs use `zY = (row+1)*TILE_SIZE` (capped to first row); back-facing chairs use `zY = (row+1)*TILE_SIZE + 1` so the chair back renders in front of the character. Chair tiles are blocked for all characters except their own assigned seat (per-character pathfinding via `withOwnSeatUnblocked`).

**Palette assignment** — a launch's look is ONE pure choice, `core/src/paletteUtils.ts` `chooseLook` (server: `paletteAssigner.assignPaletteIfNeeded(agent, store, { picked, directory })` on both surfaces; the webview's fallback for an agent the server gave no look calls it too). First match wins: a roster pick (`launchAgent.palette`, worn even if taken), else the launch Directory's **default characters** (`Directory.characters`, highest priority first, set in the Directory modal; `characterOrder` `priority` = the first one no agent wears, `random` = a random unworn one; either way all worn → fall through, a default in the office is never repeated — `core/src/directoryCharacters.ts` `pickDirectoryCharacter`), else `pickRandomPalette()`: a random character among those with the fewest copies in the office (one no agent wears while any is free, then a random repeat, never a third copy of one until every character has a second), preferring ones no Directory claims as a default (`directoryDefaults()`, so a Directory's characters stay free for its own launches). **A look is `{ palette, repeat }`**: `repeat` says which copy of its character an agent is (`repeatFor`: the lowest no other copy holds, 0 when no one wears it; teammates and sub-agents copy their lead's). The look names no colours: the nth repeat is drawn with every piece of clothing colorized to the nth colour of `REPEAT_CLOTHES_HUES` (red, blue, green, yellow, purple, cyan, pink, then more, cycling; `core/src/characters/repeatClothes.ts` `withRepeatClothes`: underwear, pants, top, outfit, jacket, shoes, hat; skin, hair, eyes and accessories stay), rendered from the profile on demand (`officeSprites` hands `setCharacterTemplates` the sheets and their repeat source together); an external `char_N.png` has no clothes to tell apart, so its repeat is hue-turned whole (`repeatHueTurn`, `adjustSprite`). Palettes = the character profiles, then any external `char_N.png` (server: `getPaletteCount()`). The launch drawer shows a Directory's defaults as 1x mug shots side by side: up to 4 all show; from 5, the first 3 (random order: 3 random ones) plus a dark blank-character silhouette with "..." (`DirectoryCharacterStrip`, `directoryStrip.ts`); pressing a mug shot launches as that character (`launchAgent.palette`), pressing the "..." shows every default (6 to a line, until the drawer closes); a drawer opened by a roster pick (`LaunchDrawer` `pick`, from `useRosterLaunch`) shows only the Directory names and launches as the pick, the rest of the row launches in the Directory's order, and a row's buttons (`drawerRowButtons.ts`: the pencil on user rows) are drawn as a small stack outside the drawer, hanging off its right border level with the hovered row (re-measured by a `ResizeObserver`); on touch a long press on the row reveals its stack instead (it never launches), a press outside hides it. Character stores `palette` (profile index) + `repeat`; older saves' looks in degrees (`clothesHue`, and `hueShift` up to v1.5) are read as "a repeat" (non-zero = 1). **A palette is an index, so the list keeps them on their character**: every profile has a permanent `id` (`char-<index>` for a list saved before ids, a fresh one for every character the cast adds, copies and loaded configs included), and a save (or a `characters.json` rewrite) that inserts or deletes characters is matched old to new by id (`core` `characterRemap`). `server/src/characterRemap.ts` renumbers this process's agents and their saved seats (an agent whose character was deleted gets a new look; a follower copies its lead's) and sends them as `characterProfilesLoaded.agentLooks`, applied with the list (`officeState.setAgentLook`); the process that saved also renumbers the machine-wide references (Directory defaults, the roster's recency, past conversations' looks) and re-sends Directories and recency. Sprite cache keyed by `"palette:repeat:blink"` (a palette that can't blink shares its open-eyed set under the blink key). **The server owns each agent's look** (picked at creation; a teammate copies its lead's): `saveAgentSeats` only fills a look an agent doesn't have yet, and a reconnect's `existingAgents` re-applies look and seat to characters the office already shows (`syncAgent`) — a stale browser saving back its old ones used to reshuffle the office for every viewer.

**Visits**: the character's errands (`Character.errands`, `engine/visitsController.ts`: the server Visit at the bottom, a local errand above it; `os.visits.start(id, stops, then)` — stops walked in order, each faced and stood at for its `lingerSec` (default `VISIT_LINGER_MS`), then `wander` / `stay` / `seat`; `end`; `stopOf`) takes the character out of the usual FSM: its agent's work doesn't move it until the visit ends (the server's `cleared` on the next turn, then an active agent heads for its seat). A repeat of the visit under way (snapshot) keeps its progress; a stop this office can't walk to drops it; a layout rebuild doesn't snap a visitor to its seat; the user's seat click / walk command ends it. **Message show** (`agentMessageShow` → `visits.showMessage(fromId, toIds, gist, { walk })`, `visits.gistOf`): a MessageShow errand pushed over the server Visit (dropping Buildout work) whose stops stand `beside` each recipient (aimed by the office — `spotBeside` around where that character stands or is walking to, re-aimed as it moves, the sender's own tile as the start) and `say` the gist while arrived (`MESSAGE_SHOW_LINGER_MS` each), then `seat`; recipients absent, leaving or unreachable are skipped; a second show queues after the first; a server `agentVisit` replaces it (server wins), a server `cleared` only drops the server Visit under it (the show carries on, then `seat`); a Visit under a finished errand is walked again. Reduced motion or no one to walk to: the gist shows in place (`ch.saying`).

**Buildout** (`layoutLoaded.buildout { agentId, origin }` — only on an agent edit's broadcast that names a tile, never undo / saves / the connect snapshot → `OfficeState.startBuildout(layout, buildout, shift)` (playing in `os.buildout`, `engine/buildoutPlayer.ts`); reduced motion or a first layout → plain `rebuildFromLayout(layout, shift)`; `layoutLoaded.shift` moves characters and pets with a resize either way): the office's state is the new layout at once, only drawing follows the plan (`engine/buildout.ts`, pure: per-tile floor/wall/carpet changes and per-uid furniture changes, diffed against the layout the office held, lined up by `shift`; a changed item dissolves as its new self appears; nearest the origin first, `BUILDOUT_STEP_SEC` apart, squeezed into `BUILDOUT_MAX_SEC`; removals — walls, floor erased to void, items gone or changed — dissolve via `renderMatrixSprite`; carpets swap without rain; Areas and pets aren't animated). The renderer reads `shownLayout()` / `shownTileMap()` / `buildout.render()`. The builder gets a BuildoutWork errand (over its server Visit, never over a Message show; a `work` stop beside the origin: typing standing up for the build's length + `BUILDOUT_WORK_TAIL_SEC` once there, then its seat); the build never waits for the walk. Any later layout ends a buildout under way (its result shows at once); another edit builds from it.

**Spawn/despawn effect**: Matrix-style digital rain animation (0.3 s). 16 vertical columns sweep top-to-bottom with staggered timing. Spawn: green rain reveals character pixels. Despawn: character pixels consumed by green rain trails. `matrixEffect` field on Character (`'spawn'`/`'despawn'`/`null`). Normal FSM is paused during effect. Restored agents (`existingAgents`) use `skipSpawnEffect: true` to appear instantly.

**Sub-agents**: Negative IDs (from -1 down). Created on `agentToolStart` with "Subtask:" prefix, or lazily by `subagentToolStart` when missing (watched background spawns, post-reload recreation). Same palette + repeat as parent. Click focuses parent terminal. Not persisted. Spawn at the closest free walkable tile to the parent's seat (the parent itself when it has none, `anchorTile`) — around it, never in a seat. They never wander and never trail a wandering lead: `updateHelper` keeps them within `HELPER_FOLLOW_RADIUS_TILES` of that home tile, walking back when it moves (a reseated lead), facing it, sitting in place (no chair under them) while working and standing while idle. Idle (stop typing) when every tracked sub-tool row is done; overlay shows the latest non-done sub-tool status, falling back to the Subtask label.

**Speech bubbles**: Permission ("..." amber dots) stays until clicked/cleared. Waiting (green checkmark) auto-fades 2 s. A Message's gist is a text bubble (`pixel-panel`, wraps at `MESSAGE_BUBBLE_MAX_WIDTH_PX`, `data-testid="agent-gist"`) that outranks the sprite ones while shown. Sprites in `spriteData.ts`.

**Sound notifications**: Ascending two-note chime (E5 → E6) via Web Audio API plays when waiting bubble appears (`agentStatus: 'waiting'`). `notificationSound.ts` manages AudioContext lifecycle; `unlockAudio()` on canvas mousedown resumes the context (webviews start suspended). Toggled via Settings modal. Persisted per-namespace in `~/.pixel-agents/config.json`.

**Office radio** (`music/`): procedural 8-bit background music in the office's bottom-right corner (phone: centred, tucked below the office's foot behind a "Swipe up for music" hint, dragged up and down as a sheet, `playerSheet.ts`). Play/pause, skip, volume, a mood (Auto or one of `MOOD_KEYS`) and a **song code** (`TOWN-5-8F3A21C0`: mood, root, seed) to share a tune or play one. A tune is fully determined by its seed, mood and root (`makeSong`), so **the order of every random draw in the composer is part of the song-code format** — `musicComposer.test.ts` pins tunes and codes; a change that moves a draw changes every shared tune. Never plays on its own (browsers start audio only from a click). Hidden or shown from Settings → Music Player (per browser). On desktop it never moves and never covers the bottom-left toolbar: as the office narrows (a narrow VS Code panel, a wide terminal drawer) it gives up the visualizer, then the tune's name and mood, down to its buttons (`playerFit.ts`; lifted above the toolbar's row it covered the layout editor's tools); the terminal drawer can't be dragged past the width that leaves the office room for both (`OFFICE_MIN_WIDTH_PX`, `hooks/drawerWidth.ts`), and in a host we can't stop from shrinking further the toolbar draws over the player. The version label rides above the player through `radioLift.ts` (`setRadioLift` / `aboveRadio`).

**Mobile shell** (standalone only): below `MOBILE_MEDIA_QUERY` the browser renders `mobile/MobileShell` instead of the desktop layout — office and terminal as two full-screen pages in a 200%-wide sliding track (both always laid out, never `display:none`, so the canvas and xterm keep dimensions); the track's transform makes it the containing block of `position: fixed`, so modals and other viewport overlays mount at App's top level, never inside the office region), the agent cards in a bottom scroller (the same `AgentCardList` as the desktop column: same cards, same server-owned order — `cardOrderLoaded`/`saveCardOrder` — so a reorder on one device moves the cards on every open office), and `MobileKeyBar` above the software keyboard. "Keyboard open" and "clamp the shell" are separate answers (`mobile/keyboardViewport.ts`, sampled by `useKeyboardViewport`) because the two resize policies differ: iOS shrinks only the visual viewport (open, and the shell is clamped to it so the PTY resizes instead of hiding its input line), Android `interactive-widget=resizes-content` shrinks both (open, nothing to clamp). Open = an editable focused AND the visual viewport `KEYBOARD_MIN_HEIGHT_PX` below the tallest height seen at the current width (per-orientation baseline). `useIsMobile` is gated on `isBrowserRuntime`: a narrow VS Code panel must never get it (it broke every VS Code e2e shard once). Navigation rules live in `useMobileShell`: the >_ / Office toggle and the edge swipe share one handler; a card tap in the office is two-step (focus the character, then open its terminal), in the terminal it switches panes; + slides over only for launches made from it (a reload re-announcing sessions stays on the office): App reacts to `useTerminalDrawer`'s `lastLaunched`, set only for the first terminal to open after `expectLaunch`, and only within `LAUNCH_ANSWER_TIMEOUT_MS` (`hooks/launchLatch.ts`): a spawn that fails opens no terminal and no message says so, and an armed latch would otherwise claim the next terminal any device opens. an arrow right of the + card (a narrow `ROSTER_ARROW_WIDTH_PX` tab beside the square +, both as tall as `AGENT_CARD_HEIGHT_PX`; accessible name "Roster", `aria-expanded`; on both pages; it points up while shut and turns down while open, and a tap toggles) opens the roster (`CharacterPicker`, a full-width strip that slides up from behind the card bar; the arrow stays to close it), not the Characters view: a tap picks the character and opens the + card's Directory drawer, whose launch carries it as `launchAgent.palette` (worn even if taken, then in the next clothes colour); a long press (`useLongPress`, as a Directory row's reveals its buttons) and the leading `+ New` slot open the Characters view on it. Desktop (both surfaces) runs the same flow (`useRosterLaunch`, hover and pin by `useHoverPin`) from the toolbar's + card, drawn like the phone's (a square `+` — accessible name "New agent" — with the roster arrow beside it, then Layout, and Settings only where no conversation sidebar holds it): the carousel shows above the toolbar without animation, and a hovered card's pencil edits; VS Code's `launchNewTerminal` honours `palette` too (`applyPickedPalette`). The terminal-pane model (active vs shown pane, socket status, `statusFor`) is `useTerminalDrawer`, shared with the desktop drawer. Touch rules: every gesture tracks ONE finger by identifier (`findTouch`) and uses one tap slop (`withinTapSlop`); gesture decisions are pure reducers with thin DOM adapters (`edgeSwipe.ts`/`useEdgeSwipe.ts`, `terminal/touchGesture.ts`/`touchInput.ts`, the radio's `music/playerSheet.ts`/`usePlayerSheet`; the key bar's trackpad sends left/right twice as fast as up/down, accelerating so a drag from the press point to a screen edge sweeps the terminal's full line (`TerminalInputHandle.cols`), and holds one axis per slide, re-deciding only after the finger rests, `touch/trackpad.ts`), because WebKit keeps addressing a gesture's events to its touchstart node — when terminal rows repaint, that node detaches and events stop bubbling, so each adapter binds "rescue" listeners on the touch target. **Terminal copy is verbatim by default**, except that a token Claude Code broke across rows (a URL, a path: `hardWrap.ts`) always comes back whole — that break's signature is one an intended newline doesn't have, and links (tap or click) follow it the same way (Cmd/Ctrl+C, the browser's Copy, the pill's Copy; paste is a long press on the input area — the cursor's row out to the prompt box's rules (`terminal/inputArea.ts`) — not a key; the same pill carries "Attach file"): re-flowing (`terminalCopyText`'s `'text'` mode) is a heuristic that joins a long row with a two-space-indented next line, which is also what YAML under a long key or a method body under a long signature look like, so re-flowing is opt-in only — Alt+C (Option+C) on desktop, "Copy as text" on the pill. Every write goes through `terminal/clipboard.ts`. **Files go to a terminal the way a native one takes a dropped file**: dropped on the pane (desktop) or picked through the input area pill's "Attach file" (phone), each is POSTed to `/api/terminal/:agentId/files` (the terminal socket's gate; streamed to disk, `TERMINAL_UPLOAD_MAX_BYTES`), saved in the host's upload directory — Settings → Save Sent Files To (`setUploadDirectory`, per namespace), else our own `~/.pixel-agents/uploads`, the one folder the server sweeps (files sent more than 7 days ago, then the oldest past 2 GB; a folder the user chose is never cleaned) — under a name that is safe on every OS and never overwrites (`photo-2.jpg`), and the saved path is pasted through xterm (one bracketed paste, which is how Claude Code tells a dropped image from typed text), quoted as that OS's terminals do (`terminalPathText`: backslashes on POSIX, double quotes on Windows). The server answers the path as text, so the browser never guesses the host's OS. **A file already on the host is not copied**: a page on a loopback hostname first asks `POST …/files/locate` with the file's name, size and modification time (all a browser knows of it; it never learns a path), and the server (`terminal/localFile.ts`, loopback `Host` only) looks for that very file — straight under the home directory, its Desktop, Downloads and Documents the upload directory and the Directories the user added, never deeper and with no search of the disk — checking candidates in a child process with a timeout (a stat of a protected macOS folder can block a background process forever). Found = its own path is pasted and nothing is uploaded; not found = the upload and a copy, as from another machine. PWA: `manifest.webmanifest` (icon paths relative — the file is served verbatim), conventional-path icons in `public/`, `?v=N` cache-busters on icon links.

**Seats**: Derived from chair furniture. `layoutToSeats()` creates a seat at every footprint tile of every chair. Multi-tile chairs produce multiple seats keyed `uid` / `uid:1` / `uid:2`. Facing direction priority: 1) chair `orientation` from catalog (front→DOWN, back→UP, left→LEFT, right→RIGHT), 2) adjacent desk direction, 3) forward (DOWN). Click character → select (white outline) → click available seat → reassign.

## Characters

The Characters view (bottom toolbar button; phone: next to Settings) designs the cast. Desktop: a modal of three panes (roster | animated preview + export sheet | wardrobe tabs). Phones: a full-screen page (pinned preview, carousels, bottom dock). `characterRenderer.test.ts` pins the six default sheets to their reference renders pixel for pixel. The character model (art, slot table, renderer, colour maths, sheet geometry, repeat clothes, profile edits and randomize) is pure core (`core/src/characters/`), so the server draws characters too (`server/src/characterArt.ts`: the same art decoded with pngjs, `characterPreviewPng`; `characterArt.test.ts` holds it to the same pins); the webview keeps only its loader (`loadWardrobe.ts`) and the UI.

- **Profile** (`core/src/characterProfiles.ts`): a permanent `id` (unique in the list, see Palette assignment), one wardrobe part id per slot (`CHARACTER_SLOTS`), `colors[key]` (`CharacterColor` = HSBC + optional exact `palette` swap), `edits[pixId(piece, part)]` (uncoloured pixel edits per frame, `{ cells }` — no revision; the renderer caches by content), `eyeShape`, `eyeRows`. Pixel set ids are `'<set>:<part>'`, built and split only by `pixId` / `parsePixId`. Format `v: 35`; `migrateCharacterProfile` brings any older one (v30 = the artifact's) up in one pass wherever profiles are read (server file, Load config) — every rename leaves ids it doesn't name alone, so no per-version gates: bodies (`flat`/`bust`) and eye shapes (`plain`/`lashes`), the eye whites piece `eyefix` → `whites` in edit keys, `rev` dropped, part renames (`PART_IDS`: the PSD layer ids `layer_9` → `business_suit`, … and parts named after people `helly_top` → `turtleneck`, …; per slot, in slots and edit keys), and the deleted retired parts replaced (bowling shirt → red `tshirt` under the `vest` in its Original colourway, uniforms → `business_suit`; their edits are dropped), and edits moved from the 7-frame sheet (every format before v35; v34 was taken by unmerged work, still 7 frames) to the 8-frame one (`widenLegacyCells`: frames rekeyed, the seated frame's cells derived like its art). The profile types are the wire contract's (generated `messages.ts`, `eyeRows` narrowed to `EYE_ROWS`); a compile-time check pins `CHARACTER_SLOTS` to the contract's part-id fields. The server only validates shape; part ids mean something only to the webview.
- **Wardrobe art** is finished pixels, one 128×96 office-layout PNG per asset, uncoloured: `<piece>/<part id>.png` (`hair/bob.png`), per body `body/<body>.png` (the doll body, its eye holes filled with lid skin so it never shows holes; the eyes cover it) + `under/`, `utop/<body>.png`, the eyes `eyes/<shape>/` (one copy for every body) = `whites` (whites and pupils, never recoloured), `iris.<rows>` (rows `top`/`bottom`/`both`: which pupil pixels take the eye colour, drawn over them) plus `lashes` — a shape has only the files it draws, a missing file draws nothing; `closed-stern/lashes.png` is the blink over Stern (it keeps Stern's brows), and `props/reading-glasses.png`, `props/paper.png` (drawn over everything in the reading frames; nothing of them lives in the eye files). An outfit may come with its tie as a sheet of its own, `tie/<outfit id>.png` (optional art; its own `tie` colour key and Outfit-tab picker, shown only when the outfit has one; uncoloured it wears the outfit's colour, so looks saved before the split are unchanged). `wardrobe.json` holds only parts (label, `neutral`, colourway `swaps`) and category palettes. Adding a part = its PNG + its line in wardrobe.json; `decodeWardrobe` fails loudly on a part without a PNG, a PNG without a part, or a wrong size. The art lives in `core/src/characters/art/`. All PNGs are inlined into the webview bundle (`import.meta.glob` + `?inline`) because VS Code serves webview resources cross-origin, which would taint the decoding canvas; `esbuild.js` copies the PNGs and wardrobe.json to `dist/assets/wardrobe/` for the server (shipped in the npm package and the .vsix through `dist/assets/`). The pose map, head pass, touch-ups and drawn eye shapes that once produced them are gone (baked once from the old MetroCity strips).
- **Slot table** (`core/src/characters/slots.ts`): a piece is defined once, in `LAYERS` (draw order; its slot, colour key, editor label and chip order, `when` underwear, `behind`, `neutral`; a `kind: 'part'` layer names the slot that picks it (`sel`), a `kind: 'eye'` layer draws from the eye folder, `rows` its eye-row variants, `filedBy` its edits' key); `shownArt` maps a profile + piece to its `Art` (path, layer, wardrobe part — never parsed back from the path), the colour → art map (`colorArt`; the first piece with a colour owns its colourways), the editor's pieces (`EDIT_PIECES`, `wornPieces` = shown and with art), `DRESS_SLOTS` (randomize) and `SlotKey` (core's `CHARACTER_SLOTS`) are derived. `TABS` carries each tab's pickers, editor piece, the underwear it offers (`underOf`, `tabPiece`) and the slot that lives inside it (`inner`: Hair's beard). The rest of the character model lives here too, as tables: `EYE_SHAPES` (label, tooltip, `drawn`/`bare`/`blinkLashes`; `eyeShape(p)` resolves the body default), `BODIES` (default eyes and underwear top, `startingUtop`), `UNDERWEAR`; a blink is `{ ...p, blink: true }` (`canBlink` decides when; the shape stays, so its rules hold). Mutations live in core's `profiles.ts` and touch only top-level fields, so the wardrobe's option thumbnails preview each card's own `wear` on a shallow copy. Underwear only shows where nothing covers it (`wornUnder` — the one definition, the editor's too), drawn over the doll body. Edit keys (`editKey`): lashes by eye shape, whites and iris by body except under a drawn shape (Lidded, Stern, Closed: by shape).
- **Renderer** (`renderer.ts`, DOM-free): per piece its art file + the profile's edits, tinted (`color.ts`, the artifact's rounding — not office/colorize.ts) and stacked in `LAYERS` order (earrings `behind` hair in the back view), then the reading glasses (not for `bare` eye shapes) and the paper. Layer and sheet caches key edits by content. Sheet geometry and the alpha threshold come from core (`sheet.ts`); the manifest is checked at load (`parseWardrobeManifest`).
- **Cast** (`cast.ts` `CastStore`, the app's instance in `castStore.ts`): one store for office and view; it knows neither the DOM nor the office — `officeSprites.ts` `startOfficeSync` subscribes (wired in useExtensionMessages, which hands the cast's messages to `castMessages.ts`), and CharactersView reports presses (`beginStep`/`endStep`). **The view edits a draft**: `profiles` is the saved list (the office, the toolbar roster and every other reader wear it); the first select/edit/add opens `draft`, a working copy the view shows, and nothing reaches the server until Save (the header's / phone bar's Save button, ⌘S): `save()` makes the draft the saved list and sends it. `dirty` = the draft is not the list it started from or was last saved as (by reference, so undoing back to it is clean). Closing with `dirty` asks (Keep editing / Discard / Save); `discard()` drops the draft. So the toolbar roster's `+ New` adds the character to the draft only — it joins the roster on Save. A foreign list replaces a clean draft and leaves a dirty one alone (saving it then wins). Undo history is `history.ts` (pure). Server owns the list (`characterProfilesLoaded`; `server/src/characterProfilesPersistence.ts` on both surfaces, like Directories); Save sends the whole list (`saveCharacterProfiles` with a client-chosen `saveId`). Every save is answered with `characterProfilesLoaded` carrying that `saveId`: broadcast to every client when it persisted (exactly the persisted list — a valid v35 list comes back byte-identical), sent to the sender alone with the list still on disk when it was refused (invalid, failed write, or a read-only client). No `saveId` = initial load or an external file change. The client keeps its in-flight saveIds: an answer acks its save and every older one; while a save is in flight, other lists are ignored (stale, or about to be overwritten: last writer wins); when idle, a list that differs replaces the local one and clears the undo history (a refused save's answer does exactly that), an equal one is its own echo and changes nothing. A reconnect re-sends unanswered saves. Adds stop at `MAX_CHARACTER_PROFILES` (status line says so). Validation is ONE deep validator, `core/src/characterProfiles.ts` `parseCharacterProfiles` (colours: finite h/s/b/c; edits: `cells[frame 0-23][pixel 0-511]` = `#rrggbb` or null), also behind Load config (`parseConfigFile`), run by the server before persisting and by the webview before drawing. Undo/redo: a press starts a step and everything until release joins it; otherwise 500 ms merges; card switches aren't steps; entries remember the editor frame.
- **Custom items** (`core/src/wardrobeItems.ts`, `characters/items.ts`, the pixel editor's Item section `ui/ItemTools.tsx`): a worn piece exports as a piece sheet (the piece alone, art + this character's edits, uncoloured, 128×96 PNG — the wardrobe art's own form; a 112×96 one from before the seated frame still imports, and older custom items decode the same way, `decodeSheet`); Import PNG turns a piece sheet back into this character's edits on the piece (`editsFromSheet`: the pixels that differ from the art); "Save as new item" bakes the piece's art + edits into a `WardrobeItem` (`{ id: 'custom_…', piece, label, base, png }`, base64 PNG), and the character wears it with those edits dropped. Items are worn like built-in parts (`profile.hair = 'custom_…'`) and take the colours of their `base` built-in part (gray-ness, colourways, palette row: `wardrobe.ts` `withItems`). Only hair, clothes and accessories (`ITEM_PIECES`), not bodies or underwear. Items live in the cast draft (added and deleted with undo, sent on Save with `saveCharacterProfiles.items`, answered and broadcast in `characterProfilesLoaded.items`, persisted to `wardrobe-items.json`; one validator, `parseWardrobeItems`). An item never changes once made, so the renderer holds the saved items and the draft's together (the office may still wear one the draft deleted); the view offers only the draft's (`offeredParts`). Deleting an item takes it off every character. Character configs and roster zips don't carry the items they wear.
- **Agents' edits** (Pixel Office MCP `edit_characters` / `undo_character_edit`, see "Pixel Office MCP"): saved through the same commit as Save (`server/src/mcp/characterEdits.ts`) and broadcast as `characterProfilesLoaded`, so an open view takes the new list like any foreign one (a clean draft is replaced, a dirty one kept). While the view's draft is dirty the office reports `charactersEditing {dirty}` and agents' edits wait (refused). `agentCharacterEditStatus` names the newest undoable agent edit; while the draft is clean the view shows "Undo <agent>'s edit" (`ui/AgentCharacterUndo.tsx`, sending `undoAgentCharacterEdit`, the same operation as the tool) and its status line names each edit as it lands ("<agent> created Naruto").
- **Exports**: Save PNG / config / roster zip / piece sheet download in the browser; in VS Code they go through `exportFile` (host save dialog).

## Layout Editor

Toggle via "Layout" button. Tools: SELECT (default), Floor paint, Wall paint, Erase (set tiles to VOID), Furniture place, Furniture Copy (`FURNITURE_PICK`: type + colour off a placed item), colour Copy (`COLOR_PICK`: colour only), Eyedropper (floor/wall), wall Copy (`WALL_PICK`: set + colour off a wall), section Select (`FLOOR_SECTION` / `WALL_SECTION`). `handleEditorTileAction` is a per-tool switch; the layout maths lives in pure `editorActions.ts` functions. Clicks on placed items (select, drag) never reach it — the canvas resolves them.

**Floor**: 7 patterns from `floors.png` (grayscale 16×16), colorizable via HSBC sliders (Photoshop Colorize). Color baked per-tile on paint. Eyedropper picks pattern+color.

**Walls**: painted like floors — pick a wall set (Plain, Brick, Wood planks, Stone, Wainscot, Office panel, Glass partition, Half panel, Cubicle: `WALL_SET_LABELS`) and an HSBC colour (Colorize mode); both are baked per tile (`tileColors` + `wallSets`), so any number of kinds and colours stand side by side, and the sliders only set the brush (walls already standing keep theirs). A stroke's first tile decides its direction (`wallDragAdding`, `wallStrokeAdds`): starting on the very wall it would paint (same set and colour) removes walls back to floor, anywhere else it paints — restyling any wall it crosses (`paintWall`). Copy (`WALL_PICK`) and the floor eyedropper on a wall take its set + colour. Furniture cannot be placed on wall tiles, but background rows may overlap walls.

**Sections** (`tileSections.ts`): the Floor and Walls panels' **Select** picks a section — every tile reachable edge to edge through tiles of the same material (floor: pattern + colour; wall: set + colour). The section under the cursor previews with a faint outline, picked ones get a solid one (both hidden for `EDIT_OUTLINE_HIDE_MS` after each restyle, so the colour being edited reads clean); Shift+click adds a section (or drops a picked one). A pick seeds the panel's brush with its look and keeps the colour sliders open; while sections are picked, the sliders and pattern / set thumbnails restyle all of them live (`restyleSection`, undo session `` `section:<n>` `` — one entry per pick). Picked tiles are fixed at the pick (a section restyled into its neighbour's look doesn't swallow it); undo / redo re-find them from the clicked tiles (`anchors`). Esc drops the pick, then closes the tool; a tool change drops it too.

**Furniture**: Ghost preview (green/red validity); `buildEditorRenderState` (`office/editor/`) builds the frame's `ghosts[]` + one `ghostValid`. R key rotates, T key toggles on/off state — a selected placed item wins over the catalog type. Drag-to-move in SELECT; **Alt-drag drops a copy** (cursor `copy`, Alt sampled live so it can flip mid-drag; the copy is left selected). The canvas only reports the gesture (`onDrop(uid, col, row, { duplicate })`); `handleDrop` → pure `dropFurniture` validates, commits and sets selection. **Desks carry their riders**: surface items standing on an `isDesk` item (`getSurfaceRiders`) move, rotate (spot swung round the desk top) and get copied with it; the whole group must fit or nothing happens. Delete button (red X) + rotate button (blue arrow) on selected items. **Dragging on empty floor draws a box** that selects every item whose footprint touches it (`furnitureInBox`, `editorState.marquee`; Shift adds to the selection; a click without a drag deselects). **Shift+click selects several items** (`selectedFurnitureUid` leads — its colour fills the sliders — plus `extraSelectedUids`; the buttons centre above the box round them all, `selectionBox`): the colour sliders and colour Copy, R, T, Delete and the buttons act on all of them (`setFurnitureColors`, `rotateFurnitureGroup` — the selection turns as one arrangement: each item turns and its spot swings round the centre of the box round their solid footprints, riders going with their desk, nothing turning unless all fit; a desk with one orientation only (`TABLE_FRONT`) keeps its shape but still turns what rides on it, alone or in a selection; electronics step the orientation cycle the other way (`turnedType`: a screen's orientation is the way its user looks, so front → right → back → left turns it clockwise on screen, a chair counter-clockwise) — `toggleFurnitureStates`, `removeFurnitureGroup`); dragging a selected item carries the selection and their riders as one group (`planFurnitureMove` `with`, `dragCompanions`), Alt-drag copies it and selects the copies, a moved selection stays selected; a plain click narrows it to the clicked item. The selection highlights hide for `EDIT_OUTLINE_HIDE_MS` after each colour change, so the colour reads clean. **Selecting a placed item closes the open tool tab and opens its HSBC colour sliders** (Reset + Copy buttons); color stored per-item in `PlacedFurniture.color?`. Hit-testing is ONE `furnitureAt` (surface items win over the desk under them) — select, drag, cursor and both Copy tools agree. Placement state is `editorState.placing: { type, color? }`: the Copy tool's lifted colour styles that copy only — `color: null` is a copied ABSENCE of colour, so an uncoloured item's copy stays uncoloured under a palette colour; `undefined` (a plain catalog pick) takes `pickedFurnitureColor` (`placementColor()`); palette sliders override either. Colour Copy takes the clicked item's colour into whichever sliders armed it, then returns to that tool.

**Undo/Redo**: 50-level, Ctrl+Z/Y. EditActionBar (top-center when dirty): Undo, Redo, Save, Reset. **Stroke-scoped undo**: every edit goes through `commitLayout(layout, session)`; edits sharing `editorState.undoSession` collapse into one entry — `'stroke'` (one floor / wall / erase / carpet click-drag), `` `color:<uid>` `` (a slider run on one item), `` `section:<n>` `` (restyles of one section pick). `null` = discrete edit (its own entry; a colour eyedrop is one). Mouse up / leave, tool change, Esc, selection changes and undo/redo end the session (`endStroke`). Area paint stays per-tile.

**Multi-stage Esc**: exit furniture pick → deselect catalog → close tool tab → deselect furniture → close editor.

**Erase tool**: Sets tiles to `TileType.VOID` (transparent, non-walkable, no furniture) **and deletes any furniture whose footprint the stroke passes through** (`removeFurnitureAt`). Right-click in floor/wall/erase tools also erases to VOID + furniture (drag-erasing supported). Context menu suppressed in edit mode.

**Grid expansion**: In floor/wall/erase tools, a ghost border (dashed outline) appears 1 tile outside the grid. Clicking a ghost tile calls `expandLayout()` to grow the grid by 1 tile in that direction. New tiles are VOID. Furniture positions and character positions shift when expanding left/up. Max: `MAX_COLS`×`MAX_ROWS` (64×64). Default: `DEFAULT_COLS`×`DEFAULT_ROWS` (20×11). Characters outside bounds after resize relocated to random walkable tiles.

**Layout model**: `{ version: 1, cols, rows, tiles: TileType[], furniture: PlacedFurniture[], tileColors?: ColorValue[], wallSets?: (number | null)[] }` (`wallSets`: each wall tile's set, parallel to `tiles`; null/absent = set 0, so older layouts keep their walls; cleared when a tile stops being a wall, shifted by `expandLayout`). Grid dimensions are dynamic. Persisted via debounced saveLayout message → `writeLayoutToFile()` → `~/.pixel-agents/layout.json`.

## Asset System

**Loading**: `esbuild.js` copies `webview-ui/public/assets/` → `dist/assets/`. Loader checks bundled path first, falls back to workspace root. PNG → pngjs → SpriteData (2D hex array, alpha≥2 = visible, `#RRGGBBAA` for semi-transparent). `loadDefaultLayout()` reads `assets/default-layout.json` as fallback for new workspaces.

**Catalog**: `furniture-catalog.json` with `id, name, label, category, footprint, isDesk, canPlaceOnWalls, groupId?, orientation?, state?, canPlaceOnSurfaces?, backgroundTiles?, interactive?` (the manifest's validated `interactive` block, carried on every asset of its furniture: `furnitureAssetsLoaded`'s catalogue is how the office and the server read the same declaration). String-based type system. Categories: desks, chairs, storage, electronics, decor, wall, misc. Wall-placeable items use the `wall` category and appear in a dedicated "Wall" tab. Asset naming convention: `{BASE}[_{ORIENTATION}][_{STATE}]` (e.g., `MONITOR_FRONT_OFF`).

**Per-furniture manifests**: Each furniture item lives in its own folder under `assets/furniture/` with a `manifest.json` that declares its sprites, rotation groups, state groups (on/off), and animation frames. Floor tiles are individual PNGs in `assets/floors/`; wall tile sets in `assets/walls/`.

**Rotation groups**: `buildDynamicCatalog()` builds `rotationGroups` Map from assets sharing a `groupId`. Supports 2+ orientations (e.g., front/back only). Editor palette shows 1 item per group (front orientation preferred). `getRotatedType()` cycles through available orientations.

**State groups**: Items with `state: "on"` / `"off"` sharing the same `groupId` + `orientation` form toggle pairs. `stateGroups` Map enables `getToggledType()` lookup. Editor palette hides on-state variants. State groups are mirrored across orientations.

**Interactive furniture** (`core/src/furniture/`, glossary "Interactive Furniture", `docs/adr/0005`; for furniture authors: `docs/external-assets.md` → "Interactive furniture"): a manifest may carry one optional `interactive` block whose parts are independent and each optional — `agentUse: "workstation"` (agents work here: the seat pairing below), `label: { name, lines?: [{ when, text }] }` (the Furniture label: the name and the FIRST line whose `when` holds; `{agent}` only on an `agentWorking`-only line, `{panel}` only on a `panelInUse`-only line), `panel: "terminal"` (what a click opens: see "PC shells"), `states: [{ state, when }]` (the first rule that holds picks a declared state). Conditions, a closed vocabulary that grows by decision: `agentWorking`, `panelInUse`, `free`; `when` is one or a list (any holds). ONE validator, `withInteractive`, runs wherever manifests are read (server `assetLoader.ts` for bundled and external asset directories alike, `core/src/assets/build.ts` for the dev server): an unknown key / agent use / panel / condition / placeholder or an undeclared state drops the whole block with a `[Furniture] <id>: interactive block dropped (…)` warning, and the furniture loads plain. ONE set of rules (`pieceRules.ts`; facts = the agent at work, the panel in use, the places a new panel may open, read-only): `pieceState` (the renderer, every frame), `pieceLabel`, `pieceClick`, composed by `pieceView` for the hover and the click; the server asks only `opensPanel` (does this piece open a terminal?); it knows no furniture by name. **Electronics no longer pair by category**: a piece is a workstation only by `agentUse`; an `electronics` piece with states and no block loads plain with a warning (`withInteractive`), and `docs/external-assets.md` says what to add. The PC (`assets/furniture/PC/manifest.json`) declares all four parts.

**Auto-state**: furniture says how it reacts in its manifest's `interactive` block (core `furniture/`), and the office evaluates it with core's rules (`pieceState` every frame, `pieceView` for hover and click); nothing in the office names the PC. `core/src/layout/workstations.ts` `pairWorkstations` pairs each seat with at most one piece whose furniture declares the `workstation` agent use (the PC) and each such piece with at most one seat: the tile in front of the seat must be a desk, the piece must stand on that desk within reach (3 tiles ahead, 1 to the side up to 2 deep) with its screen facing the seat (front PC ↔ back chair, back PC ↔ front chair, side ↔ side, left ↔ left), closest pair wins. The seat picker prefers paired seats (so sofas near a desk never count). `officeState.pieces.facts(uid, readOnly)` is what the office knows of a piece (the agent working at it — active, sitting in its seat and typing; its live PC shell as the panel in use; the Directories of its Area as the places), and `rebuildFurnitureInstances()` shows each piece in the state its rules pick (`stateVariantOf`: the same furniture and orientation in that state, animated by frame), or its usual sprite where it has no art for it (re-checked every frame in `update`). The PC declares "on" while an agent works at it or its panel is in use. Render-time only, the saved layout is untouched. Only front PCs have ON art today.

**Background tiles**: `backgroundTiles?: number` — top N footprint rows allow other furniture to be placed on them AND characters to walk through. Z-sort places bg-row items behind the host furniture.

**Surface placement**: `canPlaceOnSurfaces?: boolean` — items like laptops, monitors, mugs can overlap with all tiles of `isDesk` furniture. `canPlaceFurniture()` builds a desk-tile set and excludes it from collision checks. Z-sort: surface items get `zY = max(spriteBottom, deskZY + 0.5)`.

**Wall placement**: `canPlaceOnWalls?: boolean` — items like paintings, windows, clocks can only be placed on wall tiles. `canPlaceFurniture()` requires the bottom row of the footprint to be on wall tiles; upper rows may extend above the map. `getWallPlacementRow()` offsets placement so the bottom row aligns with the hovered tile.

**Colorize module**: `colorize.ts` with two modes selected by `ColorValue.colorize?` flag. **Colorize mode** (Photoshop-style): grayscale → luminance → contrast → brightness → fixed HSL; always used for floor tiles. **Adjust mode** (default for furniture, and an external `char_N.png`'s repeats): shifts original pixel HSL. Cache keyed by arbitrary string (includes colorize flag).

**Floor tiles**: `floors.png` (112×16, 7 patterns). Cached by (pattern, h, s, b, c).

**Wall tiles**: `assets/walls/wall_N.png`, one set each (64×128, 4×4 grid of 16×32 pieces, grayscale). 4-bit auto-tile bitmask (N=1, E=2, S=4, W=8). Sprites extend up to 16 px above tile (3D face); a lower set (Half panel, Cubicle) leaves the top of its pieces transparent. `wallTiles.ts` computes the bitmask at render time, counting a neighbour only when it is a wall of the same HEIGHT (read off the art: the lone piece's first opaque row) — so brick joins plaster, but a cubicle wall closes its own end against a full one. The mask can't see diagonals, so a piece running south keeps its side outline on a joined side (right beside a plain run, whose front face shows there); where the diagonal joins too — a wall more than one tile thick — `withoutSeams` fills that outline from the cap, so the top reads solid. `wall_0` is the original hand-drawn set; `wall_1`…`wall_8` are generated (`scripts/generate-wall-sets.mjs`), so a new kind is a texture function + one line in its `KINDS`. Colorizable via HSBC sliders. Wall sprites z-sorted with furniture/characters (`getWallInstances()` builds `FurnitureInstance[]`).

**Character sprites**: composed in the webview from the character profiles (see "Characters"), followed by `char_N.png` from external asset directories (`characterSpritesLoaded`; there are no bundled character PNGs). Each sheet 128×96: 8 frames × 16 px wide, 3 direction rows × 32 px tall. Row 0 = down, Row 1 = up, Row 2 = right. Frame order: walk1, walk2, walk3, type1, type2, read1, read2, seated (each animation's columns: `SHEET_FRAMES` in `core/src/assets/seatedFrame.ts`). The seated frame is derived from the typing frames by ONE recipe (`core/src/assets/seatedFrame.ts`), baked into every wardrobe PNG: front and back take the left half from type2 and the right half from type1 (each side's forward arm, the hand drawn in over the body; the typing frames mirror each other, so the pose is symmetric), the side view is type1 (its arm sits lower). A 112×96 `char_N.png` from before it gets the column derived on decode. Both the server's `char_N.png` decoding and the webview's composed sheets slice frames through ONE function, `core/src/assets/characterSheet.ts` `sheetToDirectionSprites`. Left = flipped right at runtime. A non-zero `repeat` swaps in the profile's sheet with its clothes recoloured (see Palette assignment).

**Load order**: `characterProfilesLoaded` → `characterSpritesLoaded` → `floorTilesLoaded` → `wallTilesLoaded` → `furnitureAssetsLoaded` → `layoutLoaded`.

## Condensed Lessons

- `fs.watch` unreliable on Windows — always pair with polling backup.
- Partial line buffering essential for append-only file reads (carry unterminated lines).
- Delay `agentToolDone` 300 ms to prevent React batching from hiding brief active states.
- **Idle detection** has two signals: (1) `system` + `subtype: "turn_duration"` — reliable for tool-using turns (~98%), emitted once per completed turn. (2) Text-idle timer (`TEXT_IDLE_DELAY_MS = 5 s`) — for text-only turns. Only starts when `hadToolsInTurn` is false; suppressed once `hadToolsInTurn` becomes true. Reset on new user prompt or `turn_duration`. Cancelled by ANY new JSONL data.
- User prompt `content` can be string (text) or array (tool_results) — handle both.
- `/clear` creates a NEW JSONL file (old file just stops).
- **A session that moves keeps its transcript.** EnterWorktree / ExitWorktree in an interactive session MOVE the whole file into the new folder's project dir (same name); a `-p` session keeps writing the old one, while its hooks name a `transcript_path` that never exists. So an agent is re-pointed only to a file that exists, once the one it reads is gone, keeping its offset — re-reading from 0 is the resume bug below (`agentMoves.ts`).
- **Resume reopens the OLD transcript.** Attaching an agent to a transcript starts at its end unless the file was born within the scan window (`fileWatcher.initialReadOffset`, shared by adoption and `reassignAgentToFile`): reading a resumed session from byte 0 replayed its history and resurrected background spawns that died with the previous process as Sub-agents that never left.
- `--output-format stream-json` needs non-TTY stdin — can't use with VS Code terminals.
- Hook-based IPC failed in early prototypes (hooks captured at startup, env vars don't propagate). HTTP `/api/hooks/:providerId` with `~/.pixel-agents/server.json` discovery works.
- PNG→SpriteData: pngjs for RGBA buffer, alpha threshold 2 (`PNG_ALPHA_THRESHOLD`), supports `#RRGGBBAA` semi-transparent pixels.
- OfficeCanvas selection changes are imperative (`editorState.selectedFurnitureUid`); must call `onEditorSelectionChange()` to trigger React re-render for toolbar.
- **External-session adoption**: scanner runs every 3 s. In hooks-OFF mode external scenarios, the test setup can race the first scanner tick. Mock-claude scenarios should give a few seconds of margin before assertions.
- **Heuristic sub-agent permission bubble timing**: the bubble lands 7 s after the SUB-TOOL is registered, not 7 s after the parent Task tool appears. Tests waiting on it from the "Subtask:" overlay need at least `1 s (Task→Bash gap) + 7 s timer + ~300 ms IPC/render = 9–10 s` budget.
- **runInBackground sub-character gate**: in webview `agentToolStart`, `runInBackground=true` Agent tools are gated out of sub-character creation when the parent has a `teamName` (teammate path handles it). With no `teamName`, the gate must be bypassed so the basic Subtask sub-character still renders. `addSubagent` dedups via `subagentIdMap`, so the bypass is safe even if a teammate is detected later. `subagentToolStart` creates the sub lazily when it's missing — covering teamed leads' unnamed background spawns and post-reload recreation.
- **Allure HTML report**: viewing via `file://` fails (browsers block `fetch()` from local files). Use `npx allure open allure-report/allure` or `npm run test:report:open`.
- **Context usage is a snapshot against a provider-declared window**, and both halves are easy to get wrong: cumulative sums measure spend rather than occupancy, `input_tokens` without the cache counters measures almost nothing, and a 200k window assumed for a 1M model reads five times too full (the number to check it against is Claude Code's own statusline `context_window.used_percentage`).

## Key Decisions

- **Layered codebase** (core → server → adapters; core → webview-ui). Standalone CLI never imports `adapters/vscode/` and vice versa.
- **AsyncAPI 3.0 contract**, generated TS bindings, CI drift check. Single source of truth for the wire protocol.
- **AgentRuntime** shared lifecycle core, composed by both surfaces.
- **AgentStateStore** as single source of truth with typed mutations and typed events. No transport calls outside the broadcast layer.
- **Transport abstraction**: `MessageTransport` interface, `PostMessageTransport` + `WebSocketTransport`. One branching point in the entire UI.
- **HookProvider** as the integration boundary, with optional file fallback. New CLIs are a single subdirectory under `server/src/providers/hook/<id>/`.
- **TeamProvider** as optional extension. Claude Agent Teams is the only implementation.
- **Per-adapter namespaced persistence** under `~/.pixel-agents/`. VS Code and standalone never clobber each other.
- **Verify-before-clear migration** for legacy VS Code state.
- **Single `WebviewViewProvider`** (panel area, not editor area).
- **Inline esbuild problem matcher** (no extra extension needed).
- **`erasableSyntaxOnly`** in webview forbids `enum` — use `as const` objects.
- **Server always starts** regardless of hooks toggle. Only hook installation is gated by the setting.
- **Consent before any FIRST settings-file write**, per provider (`hooksConsent: {providerId: 'granted'|'declined'}`, absent = unanswered; the `hooksEnabled` preference beside it is per-provider and machine-global). **Exactly one population is asked: the one with nothing of ours installed** — hooks already on disk are granted silently at startup, since that install only ever removes events. The ask is one box of the Intro's choices step (`IntroChoices.tsx`: usage bars, live updates = the hooks, the Pixel Office MCP; all off to start, a line each with the full terms behind "Read more", Continue sends them all, every box off is warned about first; ticked = `install`, left off = `never`), in the first-run tour a greeter character speaks in-app on both surfaces (`IntroBubble.tsx`: "Hi, I'm <greeter>" → "First, get Claude Code" only when `hooksConsentRequest.cliInstalled` is false (`HookProvider.isCliInstalled`, Claude: `claude` on PATH, `executableOnPath.ts`) → choices → all set); the server sends `hooksConsentRequest` during the `webviewReady` handshake, one per provider, privileged connections only, carrying the provider's own `consentDisclosure()` (headline, summary, disclosure) so no client-side copy can drift. The ask-or-not predicate, the choice→action rule, and the execution live ONCE in `server/src/providers/hook/` (`consentGate.ts` decides, `consentExecutor.ts` performs); surfaces supply only their effects. **A choice is an absolute state command, not an event** — Back re-opens the ask, so a revision undoes whatever the earlier answer left: hooks on disk, a grant a failed install recorded, or a decline's own persisted hooks-off. That is why the consent record is a tri-state and each answer commits in ONE config write; the full rule and its rejected alternatives are `docs/adr/0001`. An abort (close x, Escape) sends nothing and the whole Intro returns next open; the closing step reports the install OUTCOME, not the click.
- **`hooksStatus` is install state, `hooksEnabled` is preference.** The Settings checkbox binds to `hooksInstalled` and toggles the _displayed_ state with no optimistic local update, so it can't read "on" over an untouched settings.json and lands correct rather than flickering when an install fails. Every failure path re-derives and broadcasts the truth (standalone via `clientMessageHandler`, VS Code via `reportHooksStatus`). The hook script is copied BEFORE the entries are written; a failed copy aborts the install (entries pointing at a missing script spawn a dead `node` per event). **Hooks-off is persisted only AFTER a successful uninstall** — flipping it first strands the user: the entries keep firing while the persisted preference makes the next start skip the gate entirely.
- **Never rewrite a shape we did not author.** The unparseable-file abort generalizes: a non-object `hooks`, a non-array `hooks.<Event>`, and junk entries inside an event array are all refused or passed through, never replaced. An array `hooks` was the sharp case — string keys assigned onto it vanish from `JSON.stringify`, so the write committed and reported `installed: true` over a file with no hooks in it. Emptied event keys are deleted only when _our_ removal emptied them. **Internal sentinels must not be values user JSON can hold**: `null` marked "this entry is now empty", so a user-authored `null` inside a hooks array was silently deleted (a file with no Pixel Agents command anywhere came back rewritten and logged as "Hooks removed") — it is a `Symbol` now.
- **Hook identity is anchored at both ends, not a substring.** `includes('claude-hook.js') && includes('.pixel-agents')` claimed — and `uninstallHooks` then DELETED — a `.backup` copy of our script, a shell comment naming our path, a wrapper passing it as an argument, `/opt/evil.pixel-agents/hooks/claude-hook.js`, and `my-pixel-agents-hook.js`. Ours = the `/.pixel-agents/hooks/claude-hook.js` suffix, ending the command's FIRST token, matched **case-insensitively** (the token is normalized to lower case). Case-sensitive matching is what shipped, and on the case-insensitive volumes this runs on (macOS, Windows) a differently-cased path is the SAME INODE as our script and genuinely firing: reinstall appended a duplicate and uninstall left the cased entry as an orphan our own `areHooksInstalled` could no longer see — a live hook with no removal route. The folding is unconditional (no filesystem case-sensitivity probe), so the accepted trade is a Linux-only false positive that is **not** a mere dedup: on a case-sensitive volume `~/.Pixel-Agents/hooks/claude-hook.js` is a genuinely DIFFERENT file, we classify it as ours, and uninstall **deletes** it (`claudeHookInstaller.test.ts` pins that removal). Nothing creates that path, and the trade is deliberate — the alternative is a guaranteed unremovable live hook on the two platforms this actually ships to. A symlink alias to our script is deliberately _not_ recognized — the cost is one duplicate entry, versus deleting a stranger's hook if we resolved paths.
- **The Pixel Office MCP is injected per launch with per-agent tokens, never installed** (`--mcp-config` file under `~/.pixel-agents/`, a token minted for that agent alone, in memory only; never the server token, never a write to `~/.claude`). Chosen over a user-scope install (reaches sessions the office never launched, outlives the office, and edits Claude's config) and over handing agents the server token (any code an agent runs could then drive every message the office accepts). `docs/adr/0003`.
- **E2E over webview unit tests** for OSS friction. Community PRs change webview internals constantly; unit tests would force contributors to update internals tests on top of feature work. E2E pins user-facing behavior, which is stable across internal refactors.
