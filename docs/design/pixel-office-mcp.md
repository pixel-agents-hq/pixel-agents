# Pixel Office MCP

The full reference (moved out of `CLAUDE.md`, which keeps a summary). Why it is injected per launch with per-agent tokens: `docs/adr/0003`.

The office's MCP server (glossary: **Pixel Office MCP**, "Pixel Agents Office MCP" in full, never "Office MCP"), offered to the agents the office launches once the user consents. Server id `pixel-office` (tool names `mcp__pixel-office__…`). Why it is injected per launch with per-agent tokens rather than installed or handed the server token: `docs/adr/0003`.

**Shape**: a Streamable-HTTP route, `POST /mcp`, on the office's own Fastify server beside the hook and usage routes — standalone and VS Code's embedded server alike (GET/DELETE → 405). Stateless: every request is authenticated afresh and served by a fresh MCP server bound to its caller, so a revoked token is refused on its very next call and read-only is read per call. No stdio bridge, no `/ws` client, no second copy of office state: tools call the runtime, store, layout persistence, launcher and terminals directly. `server/src/mcp/` owns it all:

- `composeOfficeMcp.ts` = `composeOfficeMcp(surface)`, the ONE composition for both surfaces: a surface gives its `OfficeFacts` (store, provider, layout read/write, catalogue, asset counts, Directories, seats, Area mappings), its `terminals` + `deliveryGuard`, and `launch` / `close` / `pcShells` (its PC shell registry, read and written: `McpPcShells`) / `tutorial` (its TutorialSurface) where it can; it gets one `OfficeMcpFeature` (`registerRoutes`, `setEndpoint` (null: a reused server, not this office's), `offered()`, `handshake(send, afterHooksAsks?)` (nothing unless `offered()`), `replayAsk(send)` (Settings → Replay the Intro: the MCP's ask again, likewise only where `offered()`), `handleMessage`, `layoutSaved`, `clientGone`, `dispose`, and `configFor` / `revoke` for launches), the ONE `officeMcp?` that server.ts, httpServer.ts, clientMessageHandler.ts and the VS Code provider carry.
- `officeMcp.ts` = `OfficeMcp`, the ONE owner of the route, the tool table (`toolsFor`: only the tools whose `uses` the office supplies) and the per-agent token registry; its consent/status messages.
- `tool.ts` = the tool contract (`defineTool`: zod `input`, `changes` = refused while read-only, `uses` = the capabilities `run` calls (`office` is typed to them), `run(args, { caller, office, target })` → ok/refuse; `target(agentId)` defaults to the caller; `ok(value, images?)`: PNGs sent as MCP image content after the JSON text, labelled only in the JSON). `tools/` = one file per tool + `tools/index.ts` (`OFFICE_TOOLS`, the order agents see them; a new tool = its file + one line there).
- `officeOperations.ts` = the seam tools call, by capability (`OfficeCapabilities`: `agents`, `layout`, `messaging`, `visits`, `characters`, `directories`, `launch`, `close`, `shells`, `tutorial`; a surface's `OfficeOperations` has `agents` … `directories` and `tutorial` always, `launch` / `close` / `shells` only where it can — VS Code has none of the three, so it doesn't list launch_agent / close_agent or the PC shell tools). One module per capability, each with narrow non-optional deps: `agentsView.ts` (list_agents; `statusOf` = the permission bubble, else the store's `turnStatus`), `layoutOps.ts`, `messaging.ts`, `visitsOps.ts`, `charactersView.ts` (the `characters` capability's read side — list_wardrobe / list_characters, previews drawn by `characterArt.ts` — plus the ONE character resolver `findCharacter` (id, exact name, else ignoring case, or palette index; a shared name refused with the matching ids; `paletteOf` adds the external char_N.png palettes for launches) and the colour naming `namedColors` / `describeColor`), `directoryOps.ts` (the `directories` capability: list_directories' view and edit_directories' batch — the Directory modal's own save rules, `directories.ts` `withUserDirectory`, run on a copy of the user's Directories and this office's Area mappings, written once), `lifecycle.ts` (launch + close, `closeAfterTurn`), `pcShellOps.ts` (the `shells` capability: the PC shell tools over the surface's `PcShellRegistry` — `pcs()` for the PCs, `open` / `close` with the office's refusals and close question, `running` for `busy`; typing is `typeInto` with `SHELL_KEYS` = the Message keys + `ctrl+c` / `ctrl+d`, no sender tag, no screen token).
- `officeFacts.ts` = `OfficeFacts` (the surface's one `OfficePlaceFacts`, `server/src/officeFacts.ts`, shared with the PC shells, plus what only the MCP needs) + `officeSnapshot(facts)`: one per call — the layout read and migrated once (`layoutFromJson`), the catalogue, the seats with their holders (`seatOf`: the saved seat, else the given one — written once), the walk grid on first use — so one request sees one layout.
- `seatPlace.ts` = seat → tile + Area; `layoutView.ts` = get_layout / list_catalog's views; `layoutEditOps.ts` = edit_layout's ops; `layoutEdits.ts` = commit / undo / lock; `characterEditOps.ts` = edit_characters' ops (core's setPart / setColor / randomize on a copy; Directory defaults held by character id during the batch); `characterEdits.ts` = their commit (the Characters view's Save path, `commitCharacterProfiles`, then the batch's Directory writes on top of the delete's renumbering; all or nothing — a failed Directory write puts the roster back through `putBack`, undo's own step), the `charactersEditing` lock, and undo (`CHARACTER_UNDO_DEPTH` edits, each with the roster and touched Directories' defaults before/after; the newest restored only while both still hold what it wrote, so a Characters-view Save, a Directory save or a characters.json change since refuses it — surfaces call `charactersChanged()` after those; recency is not restored); `canonicalJson.ts` = the key-order-free compare both undos use; `agentLabel.ts` = how an agent is named — Nickname, else its character's name, else its Directory — for the Message tag and "Undo <agent>'s edit"; `consentCopy.ts` = the disclosure.

**Access** (`AgentMcpAccess`):

- **Injected at launch, never installed.** With consent granted, every launch and resume through the office's one launch path (standalone launcher; VS Code's terminal launch) gets `--mcp-config <file>`: the provider builds the argument (`buildLaunchCommand` `mcpConfig`; added to the user's MCP servers, never replacing them — no `--strict-mcp-config`; the starting prompt goes last, after `--`, since `--mcp-config` takes several values). Nothing is written to `~/.claude`. Agents adopted from outside the office never get it. Only Claude's launch command knows the flag.
- **Per-agent token.** `configFor(agentId)` mints a random token (`OFFICE_MCP_TOKEN_BYTES`) bound to that agent and writes the provider's `mcpConfigFile` for it (Claude: `{ mcpServers: { 'pixel-office': { type: 'http', url, headers: { Authorization: Bearer … } } } }`) to a fresh 0600 file under `~/.pixel-agents/mcp/<pid>-<rand>/agent-<id>.json` (never on the command line, where `ps` shows it; dirs of dead servers pruned at start). The registry is memory only: a token dies with its agent (`agentRemoved`), with the server (`dispose`), and all at once on a decline (`revokeAll`); `revoke` for a launch that never happened. The token IS the caller's identity — there is no other header. The master server token never reaches an agent. A request carrying `Origin` (a browser) is refused 403; an unknown token 401. A provider without `mcpConfigFile` writes no file, so its agents are offered no MCP: `configFor` mints nothing.
- **Consent** follows `docs/adr/0001`: config.json `officeMcpConsent` granted | declined (absent = unanswered = not injected), one config write per answer, Back revises. Asked on the Intro's choices step (`IntroChoices.tsx`) as one box beside the hooks and usage bars ones, all off to start, ticked = `allow`, left off = `decline`, its line and terms served by the server (`officeMcpConsentRequest` `summary` + `disclosure` — privileged sockets only, during the `webviewReady` handshake; `officeMcpConsentResponse` `allow` | `notNow` (back to unanswered, every token revoked; on the wire, not offered by the Intro) | `decline`); an office that finished the Intro before the ask existed shows the step with that box alone. Settings: an on/off switch (`setOfficeMcpEnabled`, the same disclosure as a confirm; off applies at once, no confirm) and a read-only switch (`setOfficeMcpReadOnly`, config `officeMcpReadOnly`); `officeMcpStatus` (privileged only) carries consent + read-only and is present only on a server that offers the MCP, so Settings shows the switches only there. Both effective at once for running agents. A read-only office (no token) reaches none of it.
- **Read-only** narrows the table at call time: tools with `changes` reply "read-only in Pixel Agents settings" (`OFFICE_MCP_READ_ONLY_REASON`).
- Claude Code's own MCP permission prompts still apply in the agent's terminal.

- **Layout edits**: `applyLayoutOps` runs the ops in order on a copy, every decision core's `layout/editOps.ts` (the editor's own — wall items by their top-left, never getWallPlacementRow); the first failing op refuses with its index + reason; notes for ops that changed less. `layoutEdits.ts` is the ONE commit/undo/lock: a batch saved once (layout.json read back to prove it, config `areaMappings` when changed) and broadcast `layoutLoaded` (+ `areaMappingsLoaded`) — `saveAndShow` adds `buildout { agentId, origin }` for an agent edit that names a tile, and `shift` (how a resize moved the tiles; undo sends it back) whenever non-zero. **Editing lock**: a socket's `layoutEditing {dirty}` (dropped when it closes) refuses edits and undo while any office holds unsaved editor changes (the webview's `officeMcp/agentLayoutEdits` reports it on change and after a reconnect). **Undo** keeps `LAYOUT_UNDO_DEPTH` edits with the layout (+ mappings) each replaced and restores the newest only while the office still holds what it wrote (canonical compare); the editor's "Undo <agent>'s edit" (`AgentEditUndoBar`, shown while the editor is clean; `undoAgentLayoutEdit`) is the same operation; `agentLayoutEditStatus` tells offices what undo would revert (with `refused` to the office whose press was refused).
- **Launch**: through the `launch` capability (lifecycle.ts: character + seat checked on the snapshot) → the surface's `launch` (standalone: `terminal/standaloneLaunches.ts` `launchForOffice`, the same operations as the drawer and the conversation list, so Directory defaults, characters, Areas, Worktree rules and resume checks are unchanged); the first message is the CLI's starting prompt after `--`; the seat is taken when free, else the office's pick with a note; the asks (`LaunchAsks`, one object from the tool to the launcher) are checked once by `checkLaunchAsks` — the words, and the permission mode against the provider's `permissionModes`, its `bypassPermissionMode` refused unless the office's skip-permissions setting is on. Joined = in the store and its CLI drew on its terminal and still runs `LAUNCH_JOIN_SETTLE_MS` later; else fails after `LAUNCH_JOIN_TIMEOUT_MS` (≈ 15 s). The **Nickname** is persisted on the agent (`agentCreated` / `existingAgents` `nickname`, `standalone-state.json`) and shown "Directory · nickname · worktree" on the card and the label; it is only a label (a name makes a Teammate).
- **Close**: through the `close` capability → worktreeLeave's `closeAgentAsking` (the card's ×, shared with handleCloseAgent) with the surface's `close` (standalone: `terminal/standaloneClose.ts` `closeStandaloneAgent`, the ×'s own ending). Teammates refused naming their lead, a Lead's Teammates close with it, the Worktree question becomes a refusal carrying the file count (answered by `worktree_choice` save | keep | discard + `confirmed_files`; a discard of fewer files than now is refused again), closing yourself replies first and ends you when your turn ends (`closeAfterTurn`: your next non-`active` status, else `SELF_CLOSE_FALLBACK_MS` = 10 s — ending at a fixed 1 s killed the real CLI before it wrote the closing turn to its transcript), an adopted/headless agent only leaves the office (`how`).
- **Messages**: `read_agent_terminal` renders the visible rows of the server's headless mirror of the PTY (`terminal/terminalScreen.ts` `readScreen`; token = sha256 prefix). `send_message` runs ONE delivery path (messaging.ts): the surface's `DeliveryGuard` checks (standalone `screenTokenGuard`: re-reads the recipient, compares its token; VS Code `turnGuard`), `typeInto` types through the surface's `AgentTerminals` (standalone `ptyAgentTerminals`): text as a paste (bracketed when the screen asked) tagged `[From <agentLabel>, agent <id>] `, then — the guard's `beforeSubmit` permitting — Enter as its own write after `MESSAGE_SUBMIT_DELAY_MS`; named keys (`MESSAGE_KEYS` → bytes) bare, one write each. Refused with its new screen when it changed; headless/adopted agents, Teammates and yourself refused. Delivery never waits for the show: after it, `agentMessageShow { fromId, toIds (the delivered recipients), gist }` is broadcast, fire-and-forget, never in the connect snapshot.

**In the office**: a **Visit** (`server/src/visits.ts`, `agentVisit`, re-sent in the connect snapshot) walks the character there, faces, lingers `VISIT_LINGER_MS` then wanders, or with `stay` waits until its agent's next turn; a **Message show** walks the sender to each recipient in turn with the gist in its speech bubble (`data-testid="agent-gist"`); a **Buildout** (`layoutLoaded.buildout { agentId, origin }`) builds an agent's edit outward from where its character works, removals in matrix rain, ≈ 2 s whatever its size, instant under reduced motion, never replayed to an office opened later. Details: Office UI → Visits.

**Standalone vs VS Code**: the same route and consent on both; VS Code composes it in `adapters/vscode/vscodeOfficeMcp.ts` (vscode-free, tested in `officeMcpVsCode.test.ts`) and injects `--mcp-config` into its terminal launches (VS Code has no conversation-list resume). VS Code has no screen to read: `read_agent_terminal` gives status only, and `send_message` takes text only (keys refused), only for agents that are done or active, without a token (`turnGuard`), typed through `VscodeTerminalAdapter.sendText` (the adapter's own, not core's `ITerminalAdapter`), in the provider's `terminalInputModes` (Claude: a bracketed paste), then Enter (held back if a prompt opened meanwhile). `launch_agent`, `close_agent` and the five PC shell tools aren't offered in VS Code (no `launch` / `close` / `shells` capability: its shells are integrated terminals it can't read). The tutorial's pre-approved tools include none of the PC shell tools, `read_pc_shell` included (a shell's screen can hold secrets). A second VS Code window reusing another window's server gets no MCP, and is not offered it either: the feature's `offered()` (`server/src/mcp/composeOfficeMcp.ts`: its own server serves /mcp — `setEndpoint` got a URL, not null — and the provider has `mcpConfigFile`) is false there, so its handshake sends neither `officeMcpStatus` nor the ask (a handshake before the server has started waits for `setEndpoint`).

**Testing seams**: the `/mcp` endpoint of a real composed `PixelAgentsServer` (isolated `$HOME`, the MCP SDK's client over HTTP with a per-agent token, mock-claude launched in real PTYs: `officeMcp*.test.ts`, composed in ONE harness, `server/__tests__/helpers/officeMcpHarness.ts` — `useStandaloneOffice` / `useVscodeOffice`; a suite keeps only its scenarios); the show messages applied to `OfficeState` in webview Node tests; two standalone e2e specs (`e2e/tests/standalone/office-mcp.spec.ts`: launch, read, message; `office-mcp-characters.spec.ts`: an edit_characters create joins the open office's roster and the Characters view's undo button takes it out) whose mock agent calls the tools itself from its own `--mcp-config` (the scenario step `callOfficeMcp`).
